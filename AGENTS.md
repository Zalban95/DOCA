# AGENTS.md

## Cursor Cloud specific instructions

### What this is
OpenClaw Dashboard — a single Node.js/Express web app (`server.js` + `modules/*`) that serves a static frontend (`public/`) and a JSON/SSE API for managing an external "OpenClaw" Docker/AI stack. There is one service; no database.

### The other repos in this workspace
DOCA is the hub. Three first-party clients sit beside it — `../../DocaDesk`, `../../DocaMobile`, `../../DocaWear` — each its own git repo with its own `AGENTS.md`, each speaking `/api/v1`, for all of which `PROTOCOL.md` *here* is normative.

| Repo | What it is | Which direction it talks |
|---|---|---|
| `DocaDesk` | Windows desktop client — C# / WinUI 3 / .NET 9, WebView2 around this panel | `/api/v1` out, **and back in**: it hosts its own MCP server over HTTP on the tailnet, which `modules/mcp/` connects to as a `client`-origin server. It is the only client that hosts one today. |
| `DocaMobile` | Android phone client — Kotlin / Gradle | `/api/v1` plus the SSE push loop. Also the only route by which a watch gets paired, **and the network a watch reaches this hub over** — it performs the watch's calls with the watch's own token, adding none of its own. |
| `DocaWear` | Wear OS watch client — Kotlin / Gradle | `/api/v1` **through the phone**, which carries the bytes and nothing else: the watch holds its own `watch`-scoped token and the relay envelope forwards it verbatim, so the hub still sees a watch. It is tethered and there is no Tailscale for Wear OS, so a hub on a tailnet has no address a wrist can reach — the phone's does. The direct path survives as the fallback for a LAN hub. |

Two things follow. A change to `/api/v1`, to a scope name, or to a caps field is a change to three shipped apps, and their `AGENTS.md` files record contracts this side can break in silence — `DocaWear/AGENTS.md`, "The pair-offer field contract", is the one that has already cost a day. And because DocaDesk hosts, **a tool can land on a machine that is not this one**; that is the whole reason `environment.block()` labels server origin and `placeBlock()` exists, and it is only exercisable with a real client running.

### Running
- Dev: `npm run dev` (uses `node --watch server.js` for hot reload). Prod-style: `npm start`, or `./run.sh` which also installs deps on first run and sources `.env`.
- `./run.sh enable|disable|status` manages the systemd unit `openclaw-panel.service`. **Settings → General → Start at Boot** calls the same script through `/api/startup`, so change the behaviour in `run.sh`, not in two places. Neither works in a container or any host without systemd — `/api/startup` reports `supported: false` with a reason and the toggle greys itself out, which is expected, not a bug.
- Listens on `0.0.0.0:4242` (override with `PORT`).
- The server serves **HTTPS with a self-signed cert** (auto-generated into `.certs/`), falling back to HTTP only if cert generation fails. Use `curl -k` and, in a browser, click through the "Your connection is not private" warning (Advanced → Proceed).

### Lint / test / build
- There is **no build step** (plain JS, static assets) and **no lint script**.
- **Bumping the version means regenerating the OpenAPI document.** `modules/api-v1/openapi.js` prints `Generated by the running server (vX.Y.Z)` into `info.description`, so a bump alone makes `docs/api/openapi.json` stale and `test/openapi.test.js` fail — which is the intended alarm, not a flake. Regenerate with `npm run openapi:write` (the documented `npm run openapi > docs/api/openapi.json` leaks npm's own two-line banner into the file on npm ≥ 7 unless you pass `--silent`).
- **Version discipline**: `package.json` is the only source of truth — `environment.block()`, `catalog.detect()` for the built-in harness, `/api/update-check` and the OpenAPI description all read it. Patch for a fix, minor for behaviour, and the number goes in the commit subject in brackets, as the log has done since 2.3. **Tag it too**, annotated and with a message in the same call: `git tag -a vX.Y.Z -m "…" && git push --tags` (`-a` with no `-m` opens an editor and aborts if it comes back empty, which on Windows is how a tag silently does not happen). Note that `.git/packed-refs` holds only the pre-v2.4 tags — every later one is a loose ref, so `git tag -l`, not that file, is what "which versions are tagged" means. Adding fields to an existing state file (memory entries, the session index) needs a read-side default, since there is no migration machinery: an old `.doca/harness/memory.json` must keep loading.
- `npm test` runs the `/api/v1` client-protocol suites plus the harness, MCP and VM suites with `node --test` (no external services; each file boots the app on an ephemeral HTTP port with a temp `DOCA_DATA_DIR` and `DOCA_PREFS_FILE`, so your real prefs are never touched). The harness suite talks to a scripted stub model server on an ephemeral port — no API keys or Ollama needed. `npm run client:demo` (needs a running server and `DOCA_ADMIN_TOKEN`) exercises the reference clients end to end.

### Harnesses (`/api/harness/*`)
- A harness is the agent runtime DOCA talks to. `modules/harness/catalog.js` owns the list (built-in + 14 known CLIs/stacks + user-added custom ones) and which one is the default; the Controls page and the Harness tab both render from `GET /api/harness`.
- The default on a fresh install is the **built-in DOCA harness** (`modules/harness/agent.js`), an agent loop over any OpenAI-compatible `/chat/completions` endpoint with tool calling (`tools.js`) and structured memory (`memory.js`). It stores conversations and durable memory under `DOCA_DATA_DIR/harness/`, and its model parameters under `harness.config.doca` in the prefs file.
- These are legacy dashboard routes, not `/api/v1`, so they are **not** part of the OpenAPI document and adding one does not require regenerating it.
- Selecting a model needs a reachable provider. Without one (no Ollama, no keys) the console shows "Pick a model with ⚙" — that is expected in a bare VM, not a bug.
- The system prompt is assembled in `agent.js::systemPrompt()` in a fixed order: `providers.SAFETY_CHARTER`, then the user's editable prompt, then `environment.block()`, `clientBlock()`, the memory rules, the matching memory entries, and any settings proposals. **The charter stays in code**, never in prefs — the agent it governs can propose changes to everything in prefs, so a rule it could edit would be worth nothing. Do not move it into `defaultParams()`.
- The agent's picture of **its own clients** comes from `doca_clients` (`tools.js`), which reads the `/api/v1` registry: who is paired, who is connected (`bus.isOnline`), what is queued for whoever is not, and what each device's scopes allow. Without it the agent answers "who is connected" from `ss`/`who`, which describes sockets rather than devices and cannot tell a watch from a browser tab. Sockets and tailnet peers stay a `shell`/`system_status` question, deliberately.
- **Every turn says which client asked** — `agent.turn({..., client})` renders `clientBlock()` into the prompt (who, form factor, screen, inputs, and one line on how much answer that client can hold, from `SHAPE` in `agent.js`). The `/api/v1` adapter derives it from the device's paired caps and the dashboard console hardcodes itself as a desktop browser, so no entry point is anonymous. The rule lives in `agent.js`, not in the callers, and the tag is **never** concatenated onto the user's text: provenance goes on the transcript row as `from` and `toApiMessages()` maps only the fields the API takes. A client cannot describe itself per message — the caps it paired with are the claim, which is why an app with dishonest caps gets answers shaped for the device it pretended to be.
- **The agent can now reach a person on a device, and that is one module** (`modules/harness/reach.js`, tools `ask_device` / `tell_device`). Every part of it already existed — a prompt with choices, per-device tailoring, quiet hours, expiry, durable delivery to whoever is asleep — and none of it was reachable from the harness: only a separately paired `agent`-scoped device could raise a prompt, so the thing that does the work could *see* the user's devices (`doca_clients`) and not speak to one. It calls the same `prompts`/`bus` code an external agent calls, deliberately, because a question from the built-in harness and a question from a paired agent must look identical on a wrist. Three decisions are load-bearing: **`ask()` blocks and withdraws the question on timeout** (a model asks because it cannot continue, and a question that outlives the turn that asked it leaves a watch offering choices that lead nowhere); **choices are options only** (voice/text/image answers resolve through the gateway or a paired agent — a different job, not a parameter); and **a picture is saved as the recipient's own media**, so a watch with `media:upload` and no `media:*` can read exactly the image it was sent, with no new scope, route or sharing table. `ask_device` is in `agents/registry.NEVER`: a mission runs unwatched, and a specialist that stops to ask has gone around the orchestrator that dispatched it.
- **A mission tells the devices, not just the panel.** `missions.announce()` publishes `agent.mission` to every device with `harness:chat` — durable on start and finish, ephemeral for the step ticks, because progress replayed from an hour-old queue is not progress — and `GET /api/v1/harness/missions` is the same picture for a client that has just woken up. Before this the only place a mission appeared was a bar in the panel that polls every three seconds, so a phone in a pocket could not learn that work it started had finished.
- **Somebody else's documentation is read out of context.** `research_docs` (`tools.js` → `modules/harness/research.js`) fetches the pages, strips them, and hands them to `agent.ask()` — one completion with **no tools, no memory, no environment, no client, no transcript and no charter**, whose whole system prompt is `READER_PROMPT`. The agent gets `frame()`'s report, never the page. The security property is exactly that the thing reading attacker-controlled text has nothing to act with; the report is still untrusted and the frame says so, so do not "simplify" it away, and do not let the reader grow a tool list. `http_fetch` is still there for endpoints the user owns.
- `agent.ask({system, user})` is the model without an agent around it. Use it for work that needs a model but no authority (the quarantined reader, the rules review). It resolves the harness's own provider/model and refuses when none is chosen; it is deliberately not a `turn()`.
- The rules review is `POST /api/harness/memory/rules/verify` (**never writes** — it reports `CONFLICTS/UNCLEAR/GAPS/QUESTIONS` and can be given an unsaved draft with `{rules, categories}` so the Rules modal can check before saving). Rules stay editable by exactly two authors, the user and the agent; a reviewer that edited them would be a third nobody asked for.
- `environment.js` must stay cheap: it is rebuilt on every step of every turn (8 by default) and only reads os counters, prefs and in-process state, with a 5 s cache that `settings.apply()` invalidates. Anything needing a subprocess (docker, nvidia-smi, virsh) belongs in the `system_status` tool instead.
- **The agent cannot write a setting.** `settings_propose` stores a proposal under `DOCA_DATA_DIR/harness/proposals`; only `POST /api/harness/proposals/:id/apply` — a click — writes prefs, and it re-runs `settings.refuse()` on every key because the request comes from a browser and the stored file could have been edited. What may be proposed is the `SETTABLE` prefix list; `FORBIDDEN` (whole segments: key, token, secret, password) and `PROTO` win over it. `mcpServers`, `harness.custom` and `openclaw.json` are deliberately absent: each holds a command that would later be spawned.
- Memory rules (`memory.rules()`, prefs-free, under `harness/memory-rules`) are editable by both sides — `memory_rules_write` for the agent, the **Rules** modal for the user, `DELETE …/memory/rules` to go back to `DEFAULT_RULES`. An unknown `category` on an entry is stored as given, on purpose.
- **The tool list is rebuilt on every step, not once per turn.** Only running MCP servers contribute tools, and a turn is exactly when a server starts — so a per-turn snapshot meant the agent could not use what it had just started. It did not wait: three separate turns wrote a script and spoke JSON-RPC to the listener through `shell`, which works and routes around every switch and label on the tool layer. `tools.schemas()` is an in-process registry read, so recomputing it per step is cheap, and a changed count emits a `tools` event.
- **A client tool's failure is annotated with whose machine it was about.** `mcp/tools.js::placeError()` appends one `[DOCA]` paragraph when a client-hosted tool fails with a loopback address in the text — "Cannot connect to Blender at localhost:9876" reads, from here, as a port on the DOCA host, and twice now that sent the debugging to the wrong machine. The bridge's own words are never altered (the exact string is what a user searches for) and a host-origin tool is left alone.
- **`placeBlock()` joins who asked to where a tool lands.** Both facts were already in the prompt — `clientBlock()` names the asking device, `mcp/tools.js::machineNote()` names each tool's machine — and nothing said they were related, so "look at my Blender" with a Blender on two machines had no rule behind it. The default is the asking device; the hard requirement is naming the machine when it is not theirs. Rendered only when a client-hosted server is running, since with one host there is nothing to choose between.
- **MCP timeouts are settings, and the message names them.** `McpClient.timeoutFor()` reads `mcpSettings.callTimeoutMs` / `.listTimeoutMs` from prefs (120 s / 20 s by default, ignoring anything under a second), `mcpSettings` is in `SETTABLE`, and both are listed by `settings.readable()` without needing to exist in the file first — a setting the agent cannot see is one it will never propose. The HTTP path used to surface Node's own "The operation was aborted due to timeout": no number, no owner, and no hint of the thing that matters — **the timeout stops the waiting, not the work**, so a render that outlives it still finishes and a blind retry does it twice. Both transports now say that. Note `mcpSettings` is a different key from `mcpServers`, which holds spawnable commands and stays out of reach; `sectionFor()` matches whole prefixes, so one cannot open the other.
- **Every limit names itself and says whose it is.** `modules/harness/budget.js` is the whole of it: a per-turn ledger, the `# Your limits` prompt block, and `explain()`, which turns a provider's refusal into a sentence saying whether the thing in the way is a DOCA setting (with its dotted path, so the agent can propose it) or the provider's own. Before this the only thing that stopped a long turn was a 400 rendered as four hundred characters of somebody else's JSON, which is indistinguishable from a bug. Charter rule 12 makes naming the limit standing behaviour rather than a nicety. If you add a limit, add it to `block()` and to `SETTABLE` if it lives in prefs — a limit the agent cannot name is one the user has to guess at.
- **Cached prompt tokens are read and reported separately.** Every provider caches a stable prefix and bills a re-send at a fraction — which is the whole reason `environment.block()` keeps its volatile readings last — but each spells it differently: `prompt_cache_hit_tokens` (DeepSeek), `prompt_tokens_details.cached_tokens` (OpenAI), `cache_read_input_tokens` (Anthropic-compatible). `budget.cachedOf()` reads all three. Reading none of them is how an eleven-step turn reads as 1.6M when most of it was the same prefix arriving again at a tenth of the price. The cached count is **reported, never subtracted** — the tokens really were sent; what differs is the price — and a provider that says nothing reports `null`, not `0`, because a confident 0% for a provider that never mentioned caching is the same lie in miniature.
- **Tokens are counted, and a guess is never printed as a measurement.** `complete()` asks for `stream_options: {include_usage: true}` and reads the trailing usage frame (it carries no `choices`, so it is read *before* the delta check that would skip it); a 400 costs one retry without the field, because counting is worth a round trip and never worth a failed turn. When a provider reports nothing the ledger estimates at ~4 chars/token and marks the whole report `estimated` — `report().source` is `provider`, `mixed` or `estimated` and clients draw the difference. Turns emit `usage` per step, `warning` once at `warnAt`%, and `compacted` when token pressure folds the transcript early.
- **Context compaction has two triggers now.** `summarizeAfter` (messages) is unchanged; `compactAt` (% of `contextWindow`) folds early via `memory.pendingFold(..., {force:true})` once the window is declared. `contextWindow` defaults to 0 = *nobody has said*, and everything percentage-based is skipped while it is 0 — deliberately, because the window cannot be discovered (`/models` does not report it and a local runtime's is whatever it was started with) and a wrong default is worse than none.
- **Nothing may cut between a tool call and its result.** Both cuts that shorten a transcript — the fold boundary in `memory.pendingFold` and the `historyTurns` cap in `memory.window` — used to be chosen by counting rows, and roughly half the rows in a working session are a call or its result. A window opening on a `tool` row is rejected outright (`Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`, HTTP 400 from DeepSeek), and because `summarizedThrough` is *persisted* while `shouldCompact` is only evaluated after a successful reply, one unlucky cut broke **every** later turn in that conversation: the turn died before the fold that would have moved the boundary could run, so the session could not heal. `memory.foldBoundary` now snaps the cut off any `tool` row (forward, so a group folds whole; backwards only when forward would leave nothing live), `window()` drops leading orphans — which is also what repairs a session whose stored boundary predates the rule — and `agent.js::pairedRows` is the backstop, dropping either half of a broken pair on the way out. It matches on `c.id || c.function?.name`, the same fallback the result row was written with, or a provider that sends no call ids would have every pair read as two orphans.
- **Nothing may cut inside the turn in progress, either.** Both cuts are now bounded by the last `user` row. Under token pressure `pendingFold(..., {force:true})` folds only *earlier* turns and returns null when there are none; it used to fold "the older half" of the live rows, which mid-turn meant summarising the code the agent was iterating on into 250 words, and then doing it again the next step because the tool schemas alone kept the prompt over `compactTokens`. The `historyTurns` cap likewise never drops the turn's own rows: a ten-call turn is more than 24 rows, and the cap was dropping the user's request mid-turn, from rows no summary covered yet. Both triggers stay live and the lower wins; `budget.compactReason()` names which one fired, because "47688 of 1000000" in the log read as a bug when it was `compactTokens` at 40000. The ceiling this leaves: one turn larger than the model's window is refused by the provider.
- **`environment.block()` keeps its volatile readings last, under `## Right now`.** The clock, free RAM and the uptimes used to be on the first line; this block is near the front of every prompt and is rebuilt on every step, so those lines changed the prompt's opening bytes each time and destroyed the prefix that a provider's cache and a local prefill match on. New facts go above the heading, new readings below it. It is one line to undo by accident and there is a test pinning it.
- **Memory protects what has proven out, in three ways.** `locked` is the user's settled answer: `memWrite`/`memForget` refuse it for `source: 'agent'` and only `POST /api/harness/memory/:key/lock` sets it — the same shape as a settings proposal, and for the same reason. `disputed` is how the agent says a fact turned out wrong (`memory_flag`) without deleting it, because "the docs say 9876 and nothing is listening" is worth more than the silence left by a delete; a new value clears it. `history` keeps the last three overwritten values. All three reach the prompt through `memoryBlock()`, which marks locked and disputed entries inline — an unmarked entry is one the agent may freely correct.
- **`memory_rules_write` edits in place by default.** `rulesPatch()` (add/remove/replace, by rule number or exact text) changes one rule and leaves the rest; the wholesale `rulesWrite()` is still there for the Rules modal, where the user is looking at all of them. The old tool took only the complete list, which meant an agent adding one rule had to retype twenty-nine and silently deleted every one it forgot.
- `agent.preview({message})` assembles the system prompt without sending it — what `GET /api/harness/environment` does for the environment block, for the whole prompt. It is how the prompt-order and memory-marking tests assert anything at all without an inference server.
- `test/harness-awareness.test.js` covers all of this without a model: it asserts the prompt order, the refusals, that a proposal writes nothing until applied, and that a rejection with its reason reaches the next prompt.

### The update check (`modules/update.js`)
- **It asks `git ls-remote --tags origin` first, and the GitHub API only as a fallback.** This repo is **private**, and GitHub answers the public tags API with **404** for a private repo rather than 403 — it will not confirm the repo exists. That 404 arrived here as "no tags" and reached the user as a green "up to date", so a push genuinely never showed. `ls-remote` uses the credentials that pushed the tag, needs no PAT, and reads a private repo without trying.
- `GIT_TERMINAL_PROMPT=0` and `GIT_ASKPASS=echo` are not decoration: without them a machine whose credential helper has expired blocks waiting for a username nobody is there to type, and the check hangs instead of failing.
- A token for the API fallback is read from **`GITHUB_TOKEN`/`GH_TOKEN` in the environment only**, never prefs. `/api/prefs` has no auth in front of it and a PAT there would be the leak `/api/mcp` had in 2.13.1.
- **"I looked and you are current" and "I could not look" are different answers.** The response carries `checked`, `source` and `reason`, `latest` is `null` rather than falling back to the local version, and the panel draws the third state in amber. A check that cannot fail visibly is not a check — there is a test asserting a failed check never reports the local version as the latest.
- Tags are chosen by **highest semver across a page**, not by whichever one the API returns first: lexically, `2.9.0` beats `2.21.0`, and the old code would have announced a downgrade as confidently as an upgrade.
- `LOCAL_VERSION` is read at require time on purpose — the process reports what it is *running*, not what is on disk — so a pull shows the old number until the server restarts, which `/api/update` already says.

### Specialist agents and missions (`modules/agents/`)
- **Off by default (`agents.enabled`), and off means the tools do not exist.** `tools.schemas()` drops `agent_dispatch`/`agent_results` when the flag is off, which is free because the list is rebuilt every step — and it is what makes rolling this back a *settings change rather than a release*, which was the requirement. There is a test asserting the tools are genuinely absent, not merely refused later.
- **A mission is a turn in its own session, wrapped so nobody waits for it.** It cannot be a nested turn: `_running` allows one turn per conversation, so the orchestrator would be blocked for the mission's whole duration, and the entire point is that the user keeps talking. `dispatch()` creates a session, calls `agent.turn()` **without awaiting it**, and returns an id.
- **Specialists are deliberately smaller, and that is the whole reason they exist.** A sub-agent inheriting the orchestrator's prompt costs it on every step of every mission. A profile narrows: its own short role, its own tool allowlist, `memory: false` by default, and `environmentBrief()` instead of the full environment block. There is a test pinning that a specialist prompt is *shorter* than the orchestrator's — invisible in review, one careless edit from being false.
- **Three limits are structural, not configurable.** The charter is prepended to every sub-agent prompt and a definition cannot drop it. Sub-agents **report, they do not propose** — `settings_propose` and `install_propose` are in `registry.NEVER` and stripped at normalize time, so proposals keep one owner. And **no recursion**: `agent_dispatch` is in `NEVER` too. Depth one is where the cost of a mission stays a number somebody can predict.
- **A profile overrides only what it names.** Temperature, history, the summariser and the rest stay the panel's settings, so a specialist never acquires a second set of defaults to maintain.
- **Mission state is one document per mission plus a small index** (`agents/missions`). Not one file for all of them — that rewrites the whole file per update and lets two running missions race a read-modify-write, the exact disease `store.js` exists to avoid. Not one per agent either: a mission belongs to the mission, the roster is user-editable, and deleting an agent must not delete the history of what it did. The index is what a progress bar renders from; live progress rides the event stream, the same ephemeral/durable split used everywhere else.
- Definitions are JSON files in `AGENTS_DIR` (a managed path), one per agent, with the shipped ones in code as a fallback so a fresh install has them without the directory existing. A file wins over a built-in of the same id, and deleting the file reverts rather than removes. Files are writable by the agent itself — that is how a new specialist gets built.
- **The panel edits a definition as JSON, not as a form.** The fields are few, they are documented in `registry.js`, and a form would need rewriting every time one is added — while the agent writes these files with no form at all. The modal says which three tools can never be granted, and `save()` reports `refusedTools` so the panel can say what it removed rather than storing something quietly different from what was typed.
- **The missions bar polls, and stops polling.** It is a status light rather than a transcript — the transcript belongs to a conversation nobody has open — so it refreshes every 3 s *while something is running* and clears its timer when nothing is. A timer that outlives the thing it was watching is how a quiet panel ends up making a request a second for the rest of the day.
- **A restart pauses a mission; it does not fail it, and it does not resume it.** The turn was a promise in a dead process, so without `missions.recover()` (called once when the server starts listening) the row said `running` forever and the bar above never stopped polling. `paused` keeps the work, because the mission's session still holds every step. Whether to finish is the user's call: `missions.block()` tells the orchestrator to open its next reply, from whichever device writes first, with a one-line account (what, how far, what it cost) and one short question, and `agent_resume({mission, continue})` carries out the answer. A yes resumes **in the same session**, so the specialist reads what it did instead of starting over; a no marks it `cancelled`. `agent_resume` is in `registry.NEVER`: a specialist does not answer for the user.
- Specialists are listed greyed out while the feature is off rather than hidden: "where did my agents go" is a worse question than a dim row.
- The first specialist is **`archivist`**: long-term memory, one tool (`memory_search`), no memory block of its own (it searches memory rather than having it pasted in), minimal environment. Point its `provider` at a local llama.cpp instance and it is the memory sidecar with no special-casing anywhere in the code.

### Product names (`modules/branding.js`)
- **Every name a person reads comes from one file**, because the panel will be sold under a customer's label and under whatever the public release is called, and a rename that means grepping forty files is a rename that does not happen. Overrides live in prefs under `branding`, so a private label is a settings change; the UI for it is deliberately absent until it can sit behind the admin password, since the only thing worse than the wrong name is one an agent changed.
- **The distinction that matters is branding vs identifier, and getting it wrong breaks installs.** `~/.openclaw/` and `openclaw.json` are paths that already exist on disk; `openclaw-panel.service` is a unit somebody enabled; the `openclaw` row in `catalog.js` is a real third-party product, not our label; `openclaw-dashboard` in package.json is an npm identifier; `DOCA_DATA_DIR`, the `doca` harness id and the `med_`/`job_`/`trn_` prefixes are identifiers too. **None of those are renameable.** The test: if changing the string would stop an existing machine working, it is not branding. There is a test pinning it.
- The front end fills `data-brand`, `data-brand-title` and `data-brand-text` from `GET /api/branding` at boot, and the HTML ships with the default name already in it — so a failed fetch reads correctly instead of leaving empty boxes where the product should be.

### Install proposals (`modules/harness/installs.js`)
- **The agent never supplies a command.** It picks a `kind` and an `id` from a catalog this file owns — an Ollama model, one of `services.js`'s inference services, a harness from `catalog.js` — and `apply()` invokes the panel's *existing* installer through `jobs.invokeHandler`, the same handler the Models / Services / Harness tabs call. An install proposal therefore cannot run anything a button in this panel could not already run, and there is no path from a sentence the model wrote to a shell. That, not "the user approved it", is the safety property. Keep it.
- It exists because the alternative is worse, not because installing is dangerous: the agent can already install with `shell`, and a hand-written `docker run` gets the image, ports, GPU flags and HF cache mount subtly wrong, leaving something that looks installed and does not work. The services catalog knows all of that. Charter rule 6 routes installs here and says not to use `shell` for what this covers.
- Model names are free text on purpose — nobody can enumerate Ollama's library — but they are validated to `[\\w.:/-]` and go to Ollama's `/api/pull` as JSON, never as a shell word. Services and harnesses must exist in their catalogs, and the refusal **lists what does exist**, because a dead end is worse than a no.
- `apply()` re-validates, for the same reason `settings.apply()` re-runs `refuse()`: the request comes from a browser and the stored file could have been edited in between.
- **Declined rows stay in the prompt with their reason** (`block()`), and say not to ask again. An agent that cannot see it was told no asks again, and being asked the same question twice is how a person learns to stop reading the questions.
- Installs and settings changes share one tray in the Harness tab. They are the same question — something only the user may do — and two lists would mean two places to look for an unanswered one.

### Stopping a turn, and what a prompt is made of
- **A turn belongs to the user, not to the device that started it.** `_running` holds `{turnId, ctrl, by, startedAt}` per session, and `POST /api/v1/harness/turns/:id/cancel` (by turn id *or* session id) aborts it for any device with `harness:chat`. The phone that began a runaway turn may be in a pocket; the person watching it burn tokens is at the dashboard.
- **Stopping is not failing.** The turn ends on the bus as `agent.turn` state `cancelled`, never `failed` — a client that draws a deliberate stop in red teaches the user that pressing Stop broke something.
- **Stop means the next step, and the message says so.** Abort cancels the request in flight; it does not unmake the one the provider already accepted. The tokens already spent stay spent. This is the same honesty the MCP timeout message needed ("it stopped the waiting, not the work") and for the same reason.
- In the panel, Stop is not a message we send: `sseStream` takes a `signal` now, and every SSE handler that drives a turn already ties `res.on('close')` to that turn's `AbortController`, so hanging up *is* the stop. `AbortError` is swallowed in `sseStream` rather than drawn, or every Stop paints a red error under the answer it just stopped.
- **`GET /api/harness/prompt` says where the tokens are** (`agent.breakdown()`): every prompt section, the tool schemas **by owning MCP server**, and the transcript, plus `perStep` and `worstCase = perStep × maxSteps`. It exists because percentage-of-window warnings answer "will it fit" and say nothing about cost: a turn re-sends the whole prompt on *every* step, and the first screenshot through this harness cost 1.6M tokens over eleven steps while the context never passed 155k — 15% of a million-token window, which reads as perfectly fine. A bare install is ~4k per step, so anything much above that is memory entries, MCP tool schemas or transcript, and the byOwner breakdown is what makes it actionable: a fat server can be switched off on the tools list.

### Attachments (`/api/attachments`)
- **An attachment is a file, and what the model gets is a path.** `modules/attachments.js` writes the bytes into `ATTACHMENTS_DIR` and the turn carries `[{name, path, bytes, mime}]`; `agent.js::toApiMessages()` renders `attachments.note()` onto the message the model reads. The point of the shape is that it makes **vision optional instead of load-bearing**: a path costs ~20 tokens whether it names a 2 KB CSV or a 40 MB STEP file, `read_file`/`list_dir`/`shell` already work on it, "put that one in X" is a tool call rather than a feature, and a bwkl, a log or a zip is the same thing to this code as a photo. Do not "upgrade" it into image content blocks; when there is a vision model, that becomes one optional thing done *to* a file that already exists.
- **It is not `modules/api-v1/media.js` and must not merge with it.** Media expires, is mode 0600, is addressed by a `med_` id and lives outside the workspace — all four deliberate. A device still uploads to media, and `api-v1/harness.js::post()` then copies the bytes into the attachments directory, because a reference the agent is forbidden to read is not a reference (charter rule 8). That copy is what the `FUTURE(phase 2)` refusal on `mediaId` turned into; an id that was never uploaded is now a **404**, not a silent no-op, because the device believes it sent something.
- **`ATTACHMENTS_DIR` is a managed path**, so it shows in Settings → Paths, is proposable (the `paths` prefix is in `settings.SETTABLE`), and — the reason it is registered rather than hardcoded — `paths.describe()` feeds `environment.block()`, so the agent is told where attachments live as a standing fact instead of a sentence somebody has to remember to add. `attachments.dir()` re-resolves through `describe()` on every call rather than trusting the boot constant, for the same reason every other path-using module does.
- **The directory is the index.** `list()` reads the filesystem and merges the JSON sidecar where there is one, so a file dropped in from a file manager is an attachment — keep that. The sidecar only holds what the filesystem cannot say (which device sent it, the name before it was made safe). `safeName()` strips separators, control characters and leading dots; `uniqueName()` makes `report-2.pdf` rather than overwriting somebody's `report.pdf`. There are tests pinning both.
- The 50 MB cap is on the **upload**, matching multer in `server.js`, and the refusal says the escape hatch out loud: put the file in the directory yourself and name it. Do not raise the cap to make a big file work — that is what the directory is for.
- **A panel test's DOM stub is a claim about the browser, and it has been wrong twice.** `markdown.test.js`'s stub had no `lastElementChild`, which is exactly what `mdListEl` tests before opening a nested list — so under test every nested list rendered flat and that branch had never run, while the panel drew something else (bullets came out numbered). `fold-runs.test.js` then needed `appendChild` to *detach* a node from its previous parent and `replaceWith` to clear it, or rows moved into a collapsed row stayed in both places and a transcript grew where it should shrink. The rule both times: when a stub cannot express what the real DOM does, a green test pins a shape nobody sees. Add the property to the stub, and check the feature in a browser once — the browser is where the other half of a UI lives.
- **A document is a fourth kind of media, and it opens rather than draws.** `attachments.playableKind` returns `doc` for markdown and plain text, so a plan travels the road a picture already had - copied into attachments, kept with the conversation, addressed by name, carried on `images[]` with its `kind` - and only what the client does with it differs. The panel draws a row that opens a window rendering it with the same markdown renderer the transcript uses; a phone should offer the choice (open it, or carry on in the chat); a watch should not try to show a document at all, which is what the `kind` is for. This widened what `harness:chat` can fetch to the kinds a conversation puts in front of a person; everything else in the attachments folder is still a 404 on that route.
- **The agent shows media with `show_media` (`show_image` is its old name, kept as an alias).** Images are drawn, audio and video get a `<controls>` player, and the list is the one the Files tab previews with, so a file that plays when clicked there plays when the agent sends it here. `attachments.playableKind()` decides which of the three it is, server-side, and the `kind` travels on the record — a client never parses a mime type. Caps differ because the things differ: 20 MB for a still, 200 MB for a clip. `res.sendFile` answers the byte ranges a player asks for while seeking, which is why playback works without a route of its own.
- **A voice message is an attachment plus two facts.** 🎤 in the floating chat records with `MediaRecorder`, uploads the recording as an ordinary attachment, transcribes it through the STT the call mode already uses (`POST /api/chat/transcribe`), and sends the transcript as the message. The recording rides along, because a transcript is a guess about what was said. The turn then carries a bracketed note telling the agent it was spoken and to answer as if speaking, and the reply is read back through `POST /api/chat/synthesize`. Both halves are needed: the note is what stops a spoken question being answered with three screens of prose, and the speaking is the panel's job rather than the model's. 📷 is `<input type="file" accept="image/*" capture="environment">` — the native camera, no preview and no permission of our own to manage.
- **The agent shows a picture with `show_image`, never with markdown.** The tool copies the file into attachments (so a later edit to the file cannot change what was shown), emits an `image` event *before* the Result fold, and keeps `images` on the tool row so a reload draws the same sequence; the model reads only the result line. Both chats render it with `agentImageEl()` (`utils.js`), built from elements and always pointing at `/api/attachments/:name` — a chat that draws `![](url)` fetches whatever address a prompt injection talked the model into writing, which sends the conversation to somebody else's server. png, jpeg, webp, gif, avif and svg (`attachments.IMAGE_MIME`), 20 MB. Served with `nosniff` and a sandboxing CSP because an SVG opened in its own tab is a document that can run script. Devices get `images[]` on `agent.turn` done and in transcripts, fetched from `GET /api/v1/harness/images/:name` under `harness:chat` — images only, so that scope does not read every attachment. No `loading="lazy"` on these: a lazy image in a shrink-to-fit bubble has no size, so the floating chat never fetched it.
- Only the built-in harness understands attachments. The gateway and the `claude` CLI paths in `modules/chat.js` get the message alone, which is why the composer should keep saying so rather than dropping files quietly.

### Logs (`/api/logs`)
- **One source per harness, and the three kinds are not equally served.** `modules/logs.js` is the registry. `builtin` is a *subscriber*, not a reader: the DOCA harness has no process and no file, but every turn already emits `session` / `tools` / `usage` / `warning` / `tool_call` / `tool_result` / `proposal` / `compacted`, so `agent.events` (a module-level emitter that `say()` publishes to alongside the caller's `emit`) is the stream. `stack` is `docker compose logs --follow`, which is all this route used to be. `cli` **has nothing to follow** — a terminal harness is launched by the *browser* typing into a PTY (`public/js/harness.js` → `modules/terminal.js`), so the server never sees lines, only bytes belonging to one tab, and they end with the tab. It is listed as unavailable with that reason rather than hidden or offered as a stream that never speaks; making it real means DOCA owning the launch, which is a different job.
- **A line is an object — `{ts, source, label, level, text}` — and the level is decided server-side.** The old shape was a bare string that the browser scanned in full for the word "error" to pick a colour, which cannot survive a source tag: one harness named "error-handler" would paint every line it wrote red. `levelOf()` is the fallback for text sources only, applied to the text and never to the tag. The client still accepts a bare string, so a cached copy of `logs.js` against a newer server degrades instead of printing `[object Object]`.
- **Tool arguments are logged by parameter name, never by value.** `/api/logs` has no auth in front of it — the same fact that made `GET /api/mcp` leak bearer tokens — and an argument is exactly where a key or a password sits. The names answer "which tool, called how"; the values stay in the transcript behind the panel. There is a test pinning this. `text` deltas are dropped entirely: one line per token is the conversation retyped badly.
- **Source colours come from a palette with no red and no amber in it** (`public/css/logs.css`), assigned by position in the sorted id list so a source keeps its colour across a reconnect. Red is error and amber is warning, and a source wearing either is a line you have to read twice.
- The ring buffer in `logs.js` subscribes at require time on purpose — the harness works whether or not the tab is open, and a log you can only see if you were already watching is not much of a log. It starts no process and writes no file, which is why it does not belong behind the listen path the way `registry.startAutostart()` does.

### MCP servers (`/api/mcp/*`)
- `modules/mcp/` is self-contained: `client.js` is a hand-rolled JSON-RPC 2.0 client (newline-delimited JSON over a child process's stdio, or POST for an HTTP server), `registry.js` holds the definitions in prefs under `mcpServers` plus the live clients, `tools.js` presents running servers' tools to the harness, `export.js` writes them into other agents' config files. **Do not add the official MCP SDK** — it is ESM and this project is CommonJS with seven dependencies that all pull their weight.
- **Secrets are masked on the way out of the registry, and unmasked on the way back in.** `status()` replaces every `env` and `headers` *value* with `MASK`, keeping the names; `normalize()` and `updateFromDevice()` treat an incoming `MASK` as "unchanged". Both halves are required: `GET /api/mcp` has **no auth in front of it** (only `/api/v1` does), so any tailnet peer could read a client-hosted server's bearer token and a stdio server's env — and the dashboard form reads `env` straight back into a textarea and posts it on save, so masking without unmasking would write dots over the real token the first time somebody renamed a server. The live client is built from `get()` and `export.js` reads `load()`, both raw, so nothing masked reaches a connection or an exported config. This was found because the agent curled the panel to work around a stale tool list and the token came back in the listing — `environment.js` had been careful about exactly these two fields all along, and that care was worth nothing while another route gave them away.
- **Where a tool lands is a fact the agent has to be given, not one it can infer.** A server is either on the DOCA host (same filesystem, processes and `localhost` as `shell`) or hosted by a paired client (another machine, its own `localhost`, invisible to `shell`, gone when that machine sleeps). `environment.block()` labels every row with which, and adds the three-bullet explainer **only when both kinds are present**; `mcp/tools.js::machineNote()` repeats the short version per tool, but only once any client tool exists, because it is a prompt rebuilt on every step. A name with two segments after the server id (`mcp__<client>__<their-server>__<tool>`) is a server that machine hosts in turn. This is the distinction that costs an hour of debugging when it is missing: "Blender on `localhost:9876`" means a different machine's 9876 depending on which server you asked.
- Tools reach the model as `mcp__<server>__<tool>` (OpenAI function names allow only `[A-Za-z0-9_-]`, max 64 chars, hence the slugging in `registry.slug()`), and `modules/harness/tools.js` merges them into `describe()`/`schemas()`/`call()`. **Only servers in state `running` contribute tools**, which makes the harness tool list dynamic — that is why `_harnessLoadMeta(true)` re-fetches when the ⚙ panel opens, and why `_harnessDisabledTools()` starts from the saved list instead of reading absent checkboxes as unticked.
- Nothing is started implicitly. `registry.startAutostart()` is called from the **listen path** in `server.js`, never from `createApp()`, so requiring the app (as every test does) cannot spawn somebody's child processes.
- A server that fails to start answers **200 with `ok: false`** and its stderr in `/api/mcp/:id/log`, because the panel wants to draw that, not catch it. Unknown *servers* are still 404.
- Tests use `test/fixtures/mcp-stub-server.js`, a real stdio MCP server; `--fail` makes it exit at once to exercise the failure path. No network, no installed server needed.

### Virtual machines (`/api/vms`)
- `modules/vms.js` shells out to `virsh` and `VBoxManage`. Both are optional and **neither is installed by default** — each hypervisor is reported separately with its own `available`/`error`, and "not found" is the expected state, not a bug.
- Commands run through `execFile` with an **argv array and no shell**, with `LC_ALL=C` because the state words are parsed. A VM name from the client is checked against the machines that exist before it is used, so it cannot arrive as a flag (`--all`). Do not switch this to a shell string the way `modules/docker.js` does.
- An empty libvirt list is almost always the connection URI (`virsh` defaults to `qemu:///session`, virt-manager's machines are usually in `qemu:///system`); it is settable and stored in prefs under `vms.libvirtUri`.
- The parsers (`parseVirshList`, `parseVboxList`, `parseVboxDisplay`, `normalizeState`) are exported and tested against captured real CLI output, which is how this is covered without a hypervisor.

### `/api/v1` client layer
- Spec: `PROTOCOL.md`. Developer guides: `docs/api/` (getting started, device app guide, agent guide, cookbook). Code: `modules/api-v1/`. Mint tokens with `npm run token -- issue --name x --preset admin|agent|phone|watch|viewer`. Adding a scope family does **not** reach devices already paired — their token holds the list it was minted with; `npm run token -- grant <deviceId> --preset phone` re-applies a preset without re-pairing.
- OpenAPI: `modules/api-v1/openapi.js` is the source; `docs/api/openapi.json` is generated from it (`npm run openapi > docs/api/openapi.json`) and `test/openapi.test.js` fails if it is stale or if any Express route is missing from it. When adding or changing a route, update `openapi.js` and regenerate.
- `/api/v1/harness/*` (`modules/api-v1/harness.js`) is how a **device talks to the agent**; `/api/v1/agent/*` is how the **agent acts on devices**. Opposite directions, opposite scopes (`harness:*` vs `agent`), and neither implies the other — do not merge them under one prefix however much the words suggest it. The adapter calls `harness/agent.turn()` and owns no conversation state, so the charter, the prompt order and proposals-need-a-click are the same ones the dashboard console gets; a device can read a proposal and never apply one.
- A turn's answer does **not** come back in the POST. `POST /harness/messages` returns `202 {turnId}` and the turn is published on the bus (`agent.turn` durable, `agent.text`/`agent.tool` ephemeral), so every client the user owns sees the same conversation and one that reconnects replays it. `agent.text` deltas go **only to the device that posted**: the bus has no per-type subscription, so a watch cannot decline them, and a token it cannot read is radio time it pays for. One turn per conversation (`409 turn_in_flight`) — two devices posting into one transcript would interleave it. The adapter also tags the turn with the posting device (`clientOf()`), and the transcript it returns carries `from` per row.
- Durable state goes to `DOCA_DATA_DIR` (default `.doca/`, gitignored); set it to a temp dir when experimenting.
- `server.js` exports `createApp()`; it only listens when run directly.

### The frontend (`public/`)
- One 79 KB `index.html` and 27 **classic** scripts in `public/js/` — no build step, no bundler, no framework, no ES modules. Every file is a `<script>` in global scope and the handlers are inline `onclick=` attributes calling those globals, which is why nothing here can `import` and why renaming a function means grepping `index.html` for it first.
- `nav.js` holds the tab list twice: `NAV_TABS` routes, `NAV_TAB_DEFS` draws the mobile bottom bar. A tab in one and not the other is reachable on a desktop and invisible on a phone, or the reverse.
- **A harness parameter with no box in the panel is a parameter nobody can set.** The ⚙ config form is rendered from `HARNESS_PARAMS` in `public/js/harness.js` — `{key, label, unit, attrs, hint}` per row — and `defaultParams()` in `modules/harness/providers.js` is the other half of the pair. `test/harness-awareness.test.js` greps the table against it so the two cannot drift. `contextWindow` shipped without a field in exactly this way.
- **`hint` is not decoration.** This panel is meant to end up in front of people who do not know what top-p is, and the hint is the only place anything gets explained. A new parameter without one is unfinished.
- **The `min`/`max` in `attrs` clamp a saved value, they do not advise.** The form writes back what the box holds, so a `max` set to yesterday's sensible ceiling silently rewrites a working config the next time somebody saves an unrelated field — which is how a 128 k ceiling would quietly undo a million-token window. Set them wide enough to catch a typo and no tighter.
- **How full the window is, is one ring drawn from one object.** `contextRingHtml()` in `utils.js` takes `budget.report()` — the `usage` event while a turn runs — or `status().context` / the history payload's `context` when a chat is opened, and both chats render it from the same fields, so the floating panel and the console cannot describe the same window differently. The light-orange band is the part of the window **past the fold point** (`compactAt`/`compactTokens`, whichever is lower, as a share of the window), drawn *over* the used arc and translucent: under it, it would disappear at the moment it starts to matter. It is not a warning colour — that is `budget.warning()` at `warnAt` — it is where older messages stop being kept as written. No window declared means no ring at all, the same rule every percentage here follows.
- **`tok/s` is model time, not wall-clock.** `budget` accumulates `ms` measured around the provider call only, so a turn that spent forty seconds in a `shell` tool is not reported as a slow model; `tokenRateEl()` draws it as one line under the finished answer, and it is `null` rather than `0` when nothing measured it.
- The ⚙ panel re-fetches its metadata on open (`_harnessLoadMeta(true)`) because the tool list is dynamic — starting an MCP server changes it — and `_harnessDisabledTools()` starts from the saved list rather than reading absent checkboxes as unticked.

### Environment gotchas (not bugs)
- The dashboard manages an *external* Docker Compose stack and various AI CLIs. Those tools (Docker, Ollama, nvidia-smi, huggingface-cli, etc.) are **not installed by default**. Panels that shell out to them (e.g. "All Containers" showing `docker: not found`, GPU stats, model managers) will show errors/empty state. This is expected and does not indicate the app is broken — installing Docker/etc. is optional and only needed to exercise those specific panels.
- Some sidebar stats (CPU temp, GPU) read host sensors that are unavailable in the VM and render as `-`.
- Default paths (`COMPOSE_DIR`, `CONFIG_PATH`, `SKILLS_DIR`, `WORKSPACE_DIR`, `SNAPSHOT_DIR`) derive from `~` and may not exist; override via env vars (see README "Environment Variables") or in **Settings → System → Paths**, which also creates them. Precedence is saved-in-prefs > env > default, resolved in `modules/paths.js`: overrides are written into `process.env` at boot before the constants are computed, so a saved change needs a restart, and anything acting on a path outside boot should call `paths.describe()` rather than trusting the captured constant.
- Writes go through `writeFileSafe()` / `saveConfig()` / `savePrefs()` in `modules/utils.js`, which create missing directories and keep a `.bak`. Do not reintroduce a bare `fs.writeFileSync` for a user-facing file: a config path whose parent does not exist is a normal first-run state, not an error to show the user.
- No hypervisor and no MCP server is installed either. The **VMs** tab saying `virsh not found` and the **MCP** tab being empty are correct first-run states.
- Runtime prefs are written to `.dashboard-prefs.json` and certs to `.certs/` (both gitignored).
- **The machine this is actually tested on is a Windows box.** The repo lives at `D:\doca\doca\DOCA` on the host named `portal`, beside its three clients; the panel itself runs there. An agent driving that machine over a desktop bridge should not assume it has a shell on it — mounting `D:\` into an agent workspace has been broken since a Windows update on 2026-09-08 — so the loop that works is: write files through the bridge's file-commit tool, leave a `.cmd` wrapper in `D:\doca\` that redirects **all** of its output to a log file, have it double-clicked, then read the log back. `run-both.cmd`, `test-docadesk.cmd`, `build3.cmd` and the `release-X.Y.Z.cmd` files are that pattern; copy the newest rather than inventing a new shape. A wrapper that prints to a console nobody can read has verified nothing.
