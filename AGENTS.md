# AGENTS.md

**Read `CONSTITUTION.md` first.** It is the project's base rules — what DOCA is for, its values, who may release,
what is always asked, what needs a snapshot first — and it wins over this file when they disagree. This file is how
those rules are carried out in the code.

## Cursor Cloud specific instructions

### What this is
OpenClaw Dashboard — a single Node.js/Express web app (`server.js` + `modules/*`) that serves a static frontend (`public/`) and a JSON/SSE API for managing an external "OpenClaw" Docker/AI stack. There is one service; no database.

### The other repos in this workspace
DOCA is the hub. Three first-party clients sit beside it — `../../DocaDesk`, `../../DocaMobile`, `../../DocaWear` — each its own git repo with its own `AGENTS.md`, each speaking `/api/v1`, for all of which `PROTOCOL.md` *here* is normative.

| Repo | What it is | Which direction it talks |
|---|---|---|
| `DocaDesk` | Windows desktop client — C# / WinUI 3 / .NET 9, WebView2 around this panel | `/api/v1` out, **and back in**: it hosts its own MCP server over HTTP on the tailnet, which `modules/mcp/` connects to as a `client`-origin server. It is the only client that hosts one today. |
| `DocaMobile` | Android phone client — Kotlin / Gradle | `/api/v1` plus the SSE push loop. Also the only route by which a watch gets paired, **and the network a watch reaches this hub over** — it performs the watch's calls with the watch's own token, adding none of its own. |
| `DocaWear` | Wear OS watch client — Kotlin / Gradle | `/api/v1` **through the phone**, which carries the bytes and nothing else: the watch holds its own `watch`-scoped token and the relay envelope forwards it verbatim, so the hub still sees a watch. It is tethered and there is no Tailscale for Wear OS, so a hub on a tailnet has no address a wrist can reach — the phone's does. The direct path survives as the fallback for a LAN hub. |

**The hub hands out DOCA's own Android apps** (since 2.206.0, `modules/client-apps`; Field → API keys → DOCA apps): the newest DocaMobile and DocaWear APK per app under `DATA_DIR/clients/<app>/`, uploaded or **built on the hub** from the repo folder named there (Gradle by argv, `sh gradlew` so a checkout without the executable bit builds; DocaWear's Gradle 8.12 on the JDK 21 toolchain), its version read by the SDK's `aapt2` (else the build file) — and since 2.245.4 its watch mark: both apps share the package `tech.honlab.doca`, so an APK that requires `android.hardware.type.watch` is kept only as DocaWear and one without only as DocaMobile (the watch refuses a non-watch APK itself, DocaWear 1.2.3). Every build is signed with **one key the hub keeps** (`keys/android-signing.keystore`, protected; passed to Gradle as `DOCA_SIGNING_*`, which DocaMobile's `build.gradle.kts` reads), because Android installs an update only over an app signed with the same key — today the portal PC's debug key. A device reads `GET /api/v1/clients/android/<app>` and DocaMobile ≥ 1.0.2 updates itself (Settings → Updates; automatic from Android 12 once it is its own installer).

There is also **`clients/node`** in this repository (since 2.177.0, TODO H6.2/H6.6): `doca-client`, a dependency-free Node client for any Linux, macOS or Windows machine. It pairs with a code (pinning a self-signed hub's certificate, which is then the only one it trusts), asks its person once per family, and lends `files` (inside the home folder), `shell`, and since 2.191.0 `screen`, `processes`, `apps` and `device` (`clients/node/families.js`: each runs what the OS already has, by argv, and names what is missing; a screen capture is MCP image content) as an MCP server on the tailnet address behind a bearer secret (it finds hubs with `doca-client find`, Tailscale's peers knocked on at `/api/branding`, and pairs from the panel's `doca://pair` link in one step; `doca-client enable` runs it at boot (`clients/node/boot.js`; with no terminal an undecided family stays undecided), `doca-client update` takes the hub's own copy from `GET /api/v1/clients/node`, sha256-checked — `api-v1/client-files.js`), offered through `POST /api/v1/mcp/offer` for one click; it follows `device.control` (revoke, restore, ask, refresh) and refuses a revoked family itself. `test/doca-client.test.js` pairs it with a real hub and drives it from the harness and the Files tab.

Two things follow. A change to `/api/v1`, to a scope name, or to a caps field is a change to three shipped apps, and their `AGENTS.md` files record contracts this side can break in silence — `DocaWear/AGENTS.md`, "The pair-offer field contract", is the one that has already cost a day. And because DocaDesk hosts, **a tool can land on a machine that is not this one**; that is the whole reason `environment.block()` labels server origin and `placeBlock()` exists, and it is only exercisable with a real client running.

### Where this is going
`docs/design/hive.md` (2026-10-04): installing a client makes a device part of DOCA. Every new part is
held to its four questions — **upgradable** (a new version changes it without a person redoing
anything: a schema, a default, a migration), **necessary** (not a second way of doing what exists),
**repeatable without the thinking** (what the agent got working once can run again as a recipe, not a
fresh round of reasoning), **portable** (exportable and importable as a pack). Per-device settings go to
the device's page; new capabilities land in `/api/v1` first so a client can have them.

### Working on this repository
The harness gives its agent eight rules for working on any repository (charter rules 16–23 in `modules/harness/providers.js`). This repository holds itself to the same ones, whoever is editing it, with `CONSTITUTION.md` §4–§5 on top:

- **Read the rules first** — this file, and the `AGENTS.md` of any sibling repo you touch (`DocaDesk`, `DocaMobile`, `DocaWear`); their contracts break in silence from here.
- **Leave other people's uncommitted work alone.** `git status` before you start; what is already modified or untracked (an `audit.md`, say) is not yours to stash, reset or commit.
- **A branch per task.** Merging to `main`, tagging and pushing are asked for, except by a model the admin lists in Settings → Developer → Releasing (`modules/releasing.js`, `developer.releaseUnasked`; by default Claude Opus and Fable 5+; `GET /api/developer/releasing?model=<id>`), which may release unasked (CONSTITUTION W2) — and still stops for what W3 lists. A release is a commit prefixed `[X.Y.Z]` plus an annotated tag `vX.Y.Z` (see version discipline below).
- **The way back first.** Before a risky step (rewriting git history, deleting or migrating files or data, a machine's state) make a snapshot and say where it is (CONSTITUTION S9). Never restore a backup onto the live panel — a sandbox only. A restart or a version switch waits for running turns, calls and device commands (`harness/drain.js`, the default since 2.222.0); `now: true` is a person's choice, not a script's.
- **Some files ask first** (CONSTITUTION S11): a change that widens what an agent may do or weakens a guard — the charter, `modules/auth/**`, approval, `settings.js`'s lists, secrets masking and `PROTECTED_FILES`, `NEVER`/`AIRLOCK_ONLY`, `/api/v1` scopes, keys — waits for a yes, even inside a loop.
- **One logical change per commit, and the message says why.** A pure move and a behaviour change go in separate commits, so the move can be reviewed as a move.
- **Done means checked:** `npm test` green, and for a front-end change the page actually loaded with every tab visited and no page error. Report what you ran and what it printed, and what you did not check.
- **Shape:** one idea per file, new files aiming at 250 lines; `test/structure.test.js` holds files under 400 lines (the oversized ones listed there may only shrink) and front-end globals unique. Split along seams instead of raising a number.
- **Leave the tree clean:** no stray files, logs or `.bak`s (`write_file` now keeps its backups under `.doca/harness/backups/`), no lockfile churn you did not mean.
- **The agent proposes, a person decides** — the rule every feature here follows (`settings_propose`, `install_propose`, `work_plan`). A new feature that lets the agent change what governs it without a click is a bug, not a shortcut (`ISSUES.md` H-19).

### Accounts and rights (since phase 1 of docs/design/auth.md)
- **Every dashboard request passes `modules/auth/gate.js`**: a session cookie, a role holding the route's right, a sign-in within 12 h for `host`/`users`/`org`, and — for anything that changes state — a request from the panel's own page. `/api/v1` keeps its bearer tokens.
- **A new group of panel routes needs a row in `modules/api-v1/coverage.js`** (since 2.201.0, TODO H11.3): where a device gets the same capability under `/api/v1`, or why it is the panel's alone (mostly the machine's own administration). `test/api-coverage.test.js` walks the app's routes and fails on a group without one, and checks each named `/api/v1` path exists — so "every capability lands in /api/v1 first" is checked, not remembered. `api-v1/yours.js` is where a person's recipes, schedules and face reached devices.
- **A new route needs a row in `modules/auth/rights.js`.** Unmapped routes are refused (`no_rule`), and `test/auth.test.js` walks every route the app registers and fails on one without a row. Decide the right by what the route can *do*: anything that is the machine, or lets the agent act on it (approving tool calls, Auto mode, a specialist's tools), is `host`.
- **Auth state is read and written only through `modules/auth/store.js`**, whose functions are queries; `test/auth-store.test.js` is its contract, so a database can replace it as one file.
- **What the agent may do for a person is one decision: `modules/auth/permits.js`** (auth phase 2, 2.139–2.140, docs/design/permissions.md). The person's **level** (`auth/levels.js`: built-ins viewer/member/admin/owner, plus levels an admin makes, each with rights, settings prefixes, a tool policy and an approval policy) is the agent's ceiling; **grants** (`auth/grants.js`, table `grants`) are recorded exceptions — to a user, a specialist type, a mission or a session — given only by someone holding `delegate` (or an agent, to the mission it dispatched, via `permission_grant`), never beyond what the giver holds. `tool-calls.js` asks `permits.tool()` before the approval gate: outside the level and ungranted is refused with who could grant it; an `ask` level (every level without host) forces the question in any mode, which the person answers for their own call — their "always" becomes their own `approve:` grant, not the panel's allowlist. The rules (charter, control plane, `NEVER`) are checked first and are not grantable. Applying a proposal is bounded by the applier's level's settings. No person on a turn means not narrowed (pre-accounts behaviour).
- **A conversation belongs to a person: `modules/harness/session-access.js`** (since 2.145.0, found by the live test). The first person to write in a conversation owns it (and its work chats and missions, through `ancestors`); someone holding host uses every conversation, anyone else only their own — the rest answer 404 on the dashboard routes and `/api/v1` alike, as if absent. The global *active* pointer, where a turn with no conversation named goes, is the host's: a member creating or opening a chat no longer moves it, and their own unnamed turn goes to their newest conversation (or a new one). A host's "always" on a member's level-asked call is that member's `approve:` grant, since the panel allowlist never governs a member's turns. The same scope holds for the agent: `recall_conversations` searches and reads only what the person the turn acts for may open. Without host, the shared durable memory is read-only (`/api/harness/memory` writes are host until per-person memory), `/api/auth/me` carries `rights`, and the panel leaves out the machine's tabs (`HOST_TABS` in `nav.js`) rather than drawing them as refusals. Tools in `approval.FREE` (they act on nothing: reporting up, reading memory, showing a picture) pass any level without being listed.
- **Tests are signed in for you:** `H.start()` makes an owner and `H.api()` sends their cookie; `H.signIn('member')` makes someone else; `{ Cookie: '' }` makes a call as nobody. A test that `fetch`es directly must send `H.owner.cookie`.

### Running
- Dev: `npm run dev` (uses `node --watch server.js` for hot reload). Prod-style: `npm start`, or `./run.sh` which also installs deps on first run and sources `.env`.
- **Starting is `bin/doca-launch.js`, the same on Linux, Windows and macOS** (since 2.152.0, hive.md §7): `.env`, the version in `.releases/current`, a switched-to version watched for 90 s and put back if it does not answer. `./run.sh` (start) delegates to it, and a version switch restarts through it (`releases.restartSelf`), so a Windows or macOS host restarts like a Linux one. Start at boot: `./run.sh enable|disable|status` manages the systemd unit `openclaw-panel.service` on Linux; on Windows the launcher adds a Task Scheduler entry at sign-in, on macOS a launchd agent (`node bin/doca-launch.js enable|disable|status`). **Settings → General → Start at Boot** calls the same per OS through `/api/startup`. Where none exists (a container) `/api/startup` reports `supported: false` with a reason and the toggle greys itself out. **What this host can do** is `GET /api/host/capabilities` (Settings → System → This host).
- **What this machine has for DOCA is Settings → System → System tools** (`modules/system-tools-catalog.js`, refreshed in 2.203.0): each row is found by `detect.js` (no shell) and installed with **this OS's** command — `linux` through whichever of apt, dnf or pacman the machine has, `darwin` through Homebrew, `win32` through winget in PowerShell; a row with none for this OS shows its link. Groups: required (Node, npm — never updated from inside the panel they run), recommended, optional (for the features that use them; OpenClaw is one), and **for building DOCA's apps** (JDK, Android SDK, .NET 9 — never needed to run DOCA). `test/system-tools.test.js` keeps apt off a Mac and bash off Windows.
- **Installing is `scripts/install.sh` (Linux, macOS) and `scripts/install.ps1` (Windows)** (since 2.174.0, TODO H1.8): Node 22.5 checked (instructions, not an install — it is the system's), the code cloned or copied from a checkout (tracked files only, so a checkout's `.env`, prefs and data never travel), `npm ci`, the boot entry through `bin/doca-launch.js enable`, the panel started (systemd started explicitly, launchd at load, the Windows task run now, else detached with its output in `doca.log`), and the way to finish setup printed. CI runs both on all three runners from the checkout with `--no-boot` and checks the installed panel answers.
- Port `4242` (override with `PORT`). Accepts only loopback and the tailnet (`modules/listen.js`; `DOCA_LISTEN=local|tailnet|lan|all`, default `tailnet`; since 2.233.0 also Settings → System → Network, prefs `network.listen`, from the next start). **`lan`** adds the local network (private addresses at both ends) so a phone on the Wi-Fi pairs without Tailscale; **from outside loopback and the tailnet the machine's rights (host, org, users, devices, delegate) are refused** by `auth/gate.js` (`network.limited`) and left out of `/api/auth/me`, unless the admin sets `network.lanAdmin`. 📱 in the header shows the hub's addresses as QR codes (`GET /api/hub/links`: MagicDNS name, tailnet and, when allowed, LAN addresses); a phone's browser (not the app, whose user agent carries `DocaMobile/`) is offered the app after sign-in — accounts and rights (below) guard every request, and the network is the outer wall. Opening it to `all` is a decision for the owner, not a fix for a connection problem. **The inference services DOCA starts publish their ports on this machine only** (since 2.240.0, `network.services`: `local` by default, `tailnet`, `all`; `network.publish()` in services.js) — a container port on every interface was reachable from the LAN with no sign-in, around the listen rule.
- The server serves **HTTPS with a self-signed cert** (auto-generated into `.certs/`), falling back to HTTP only if cert generation fails. Use `curl -k` and, in a browser, click through the "Your connection is not private" warning (Advanced → Proceed).

### Lint / test / build
- There is **no build step** (plain JS, static assets) and **no lint script**.
- **Bumping the version means regenerating the OpenAPI document.** `modules/api-v1/openapi.js` prints `Generated by the running server (vX.Y.Z)` into `info.description`, so a bump alone makes `docs/api/openapi.json` stale and `test/openapi.test.js` fail — which is the intended alarm, not a flake. Regenerate with `npm run openapi:write` (the documented `npm run openapi > docs/api/openapi.json` leaks npm's own two-line banner into the file on npm ≥ 7 unless you pass `--silent`).
- **Version discipline**: `package.json` is the only source of truth — `environment.block()`, `catalog.detect()` for the built-in harness, `/api/update-check` and the OpenAPI description all read it. Patch for a fix, minor for behaviour, and the number goes in the commit subject in brackets, as the log has done since 2.3. **Tag it too**, annotated and with a message in the same call: `git tag -a vX.Y.Z -m "…" && git push --tags` (`-a` with no `-m` opens an editor and aborts if it comes back empty, which on Windows is how a tag silently does not happen). Note that `.git/packed-refs` holds only the pre-v2.4 tags — every later one is a loose ref, so `git tag -l`, not that file, is what "which versions are tagged" means. Adding fields to an existing state file (memory entries, the session index) needs a read-side default, since there is no migration machinery: an old `.doca/harness/memory.json` must keep loading.
- **`npm run smoke` opens the panel in a real browser** (`bin/doca-smoke.js`, since 2026-10-05): the installed Chrome/Edge/Chromium (or `CHROME=`) headless over the DevTools protocol, against the panel in a child process on throwaway data, every tab visited, the Settings sub-tabs that draw themselves and `/face`; any page error or failed load fails it. CI runs it after `npm test` on Linux, Windows and macOS, which is how "the panel loads on a Mac" is checked rather than assumed. The panel runs in a child that is killed at the end because node-pty's reader keeps a process alive after its shell is gone and aborts it on `exit()`. Without a browser it says so and passes.
- `npm test` runs the `/api/v1` client-protocol suites plus the harness, MCP and VM suites with `node --test` (no external services; each file boots the app on an ephemeral HTTP port with a temp `DOCA_DATA_DIR` and `DOCA_PREFS_FILE`, so your real prefs are never touched). The harness suite talks to a scripted stub model server on an ephemeral port — no API keys or Ollama needed. `npm run client:demo` (needs a running server and `DOCA_ADMIN_TOKEN`) exercises the reference clients end to end.

### Harnesses (`/api/harness/*`)
- A harness is the agent runtime DOCA talks to. `modules/harness/catalog.js` owns the list (built-in + 14 known CLIs/stacks + user-added custom ones) and which one is the default; the Controls page and the Harness tab both render from `GET /api/harness`.
- The default on a fresh install is the **built-in DOCA harness** (`modules/harness/agent.js`), an agent loop over any OpenAI-compatible `/chat/completions` endpoint with tool calling (`tools.js`) and structured memory (`memory.js`). It stores conversations and durable memory under `DOCA_DATA_DIR/harness/`, and its model parameters under `harness.config.doca` in the prefs file.
- These are legacy dashboard routes, not `/api/v1`, so they are **not** part of the OpenAPI document and adding one does not require regenerating it.
- Selecting a model needs a reachable provider. Without one (no Ollama, no keys) the console shows "Pick a model with ⚙" — that is expected in a bare VM, not a bug.
- The system prompt is assembled in `turn/prompt.js::systemPrompt()` in a fixed order: `providers.SAFETY_CHARTER`, then the user's editable prompt, then `environment.block()`, `clientBlock()`, the memory rules, the matching memory entries, and any settings proposals. **The charter stays in code**, never in prefs — the agent it governs can propose changes to everything in prefs, so a rule it could edit would be worth nothing. Do not move it into `defaultParams()`.
- The agent's picture of **its own clients** comes from `doca_clients` (`tools.js`), which reads the `/api/v1` registry: who is paired, who is connected (`bus.isOnline`), what is queued for whoever is not, and what each device's scopes allow. Without it the agent answers "who is connected" from `ss`/`who`, which describes sockets rather than devices and cannot tell a watch from a browser tab. Sockets and tailnet peers stay a `shell`/`system_status` question, deliberately.
- **Every turn says which client asked** — `agent.turn({..., client})` renders `clientBlock()` into the prompt (who, form factor, screen, inputs, and one line on how much answer that client can hold, from `SHAPE` in `modules/harness/turn/client.js`). The `/api/v1` adapter derives it from the device's paired caps and the dashboard console hardcodes itself as a desktop browser, so no entry point is anonymous. The rule lives in `agent.js`, not in the callers, and the tag is **never** concatenated onto the user's text: provenance goes on the transcript row as `from` and `toApiMessages()` maps only the fields the API takes. A client cannot describe itself per message — the caps it paired with are the claim, which is why an app with dishonest caps gets answers shaped for the device it pretended to be.
- **The agent can now reach a person on a device, and that is one module** (`modules/harness/reach.js`, tools `ask_device` / `tell_device`). Every part of it already existed — a prompt with choices, per-device tailoring, quiet hours, expiry, durable delivery to whoever is asleep — and none of it was reachable from the harness: only a separately paired `agent`-scoped device could raise a prompt, so the thing that does the work could *see* the user's devices (`doca_clients`) and not speak to one. It calls the same `prompts`/`bus` code an external agent calls, deliberately, because a question from the built-in harness and a question from a paired agent must look identical on a wrist. Three decisions are load-bearing: **`ask()` blocks and withdraws the question on timeout** (a model asks because it cannot continue, and a question that outlives the turn that asked it leaves a watch offering choices that lead nowhere); **choices are options only** (voice/text/image answers resolve through the gateway or a paired agent — a different job, not a parameter); and **a picture is saved as the recipient's own media**, so a watch with `media:upload` and no `media:*` can read exactly the image it was sent, with no new scope, route or sharing table. `ask_device` is in `agents/registry.NEVER`: a mission runs unwatched, and a specialist that stops to ask has gone around the orchestrator that dispatched it.
- **A mission tells the devices, not just the panel.** `missions.announce()` publishes `agent.mission` to every device with `harness:chat` whose owner may open the conversation (`session-access.hears`, since 2.147.0 — likewise `agent.turn`, work chats and the Orchestrator's automatic replies) — durable on start and finish, ephemeral for the step ticks, because progress replayed from an hour-old queue is not progress — and `GET /api/v1/harness/missions` is the same picture for a client that has just woken up. Before this the only place a mission appeared was a bar in the panel that polls every three seconds, so a phone in a pocket could not learn that work it started had finished.
- **Somebody else's documentation is read out of context.** `research_docs` (`tools.js` → `modules/harness/research.js`) fetches the pages, strips them, and hands them to `agent.ask()` — one completion with **no tools, no memory, no environment, no client, no transcript and no charter**, whose whole system prompt is `READER_PROMPT`. The agent gets `frame()`'s report, never the page. The security property is exactly that the thing reading attacker-controlled text has nothing to act with; the report is still untrusted and the frame says so, so do not "simplify" it away, and do not let the reader grow a tool list. `http_fetch` is still there for endpoints the user owns.
- **`web_search` searches through the owner's provider** (since 2.170.0, `modules/search`): SearXNG (`search.url`, no key), Brave or Tavily (a key in `DATA_DIR/keys/search.json`, mode 0600 and in `PROTECTED_FILES`), or DuckDuckGo's HTML page (no key — the fallback, parsed from a captured real page in the tests). Results are title, address and snippet, never a page; the harness frames them as external content (`untrusted.sourceOf`), and the tool is in `registry.AIRLOCK_ONLY`, so while specialists are on only the scout and the researcher search. Settings → Harness → Web search; `/api/search/*` is host.
- `agent.ask({system, user})` is the model without an agent around it. Use it for work that needs a model but no authority (the quarantined reader, the rules review). It resolves the harness's own provider/model and refuses when none is chosen; it is deliberately not a `turn()`.
- The rules review is `POST /api/harness/memory/rules/verify` (**never writes** — it reports `CONFLICTS/UNCLEAR/GAPS/QUESTIONS` and can be given an unsaved draft with `{rules, categories}` so the Rules modal can check before saving). Rules stay editable by exactly two authors, the user and the agent; a reviewer that edited them would be a third nobody asked for.
- `environment.js` must stay cheap: it is rebuilt on every step of every turn (8 by default) and only reads os counters, prefs and in-process state, with a 5 s cache that `settings.apply()` invalidates. Anything needing a subprocess (docker, nvidia-smi, virsh) belongs in the `system_status` tool instead.
- **Every setting is declared once: `modules/settings-schema.js`** (since 2.160.0, TODO H2.1). Each top-level prefs key says whether it travels (`state-map.PREFS` is built from it), its home — the hive, a device (`on: 'host'` for the machine DOCA runs on, `on: 'screen'` for how one screen shows the panel) or a person — where the agent may propose (`settings.SETTABLE` is built from `propose`), and its typed leaves with defaults: `schema.value('computers.maxRunning')` reads the prefs file through the type and falls back to the default, so a default changed there reaches every install that never set one. `readable()` lists the declared leaves of proposable sections with their hints. A new prefs key goes there first; `test/settings-schema.test.js` and the state-map scanner fail otherwise.
- **A renamed or moved prefs key is a migration** (since 2.178.0, `modules/migrations.js`, TODO H2.5). A changed default needs none — `schema.value()` falls back to the declared default — but a key that moves would sit unread in every older file. Each migration is a row in `MIGRATIONS` (`move(from, to)`, `defaultChanged(at, was, now)`, `drop(at)`; idempotent, the newer key wins when both exist) run once per prefs file when the server starts, before `createApp` (so a restored backup or a file copied from an older install is brought forward at its next start). The file is copied to `DATA_DIR/migrations/` first (last ten kept), and what ran is recorded in the file itself under `migrations.applied`/`log`, so the record travels with it; a new file is born having had every migration its code knows (`savePrefs` → `stamp()`), so a value a person picks later is never mistaken for an old default. Settings → System → This host lists them (`GET /api/settings/migrations`). An id is never edited or reused once released. Switching back to an older version does not undo one: the copy in `migrations/` is the way back.
- **The agent cannot write a setting.** `settings_propose` stores a proposal under `DOCA_DATA_DIR/harness/proposals`; only `POST /api/harness/proposals/:id/apply` — a click — writes prefs, and it re-runs `settings.refuse()` on every key because the request comes from a browser and the stored file could have been edited. What may be proposed is the `SETTABLE` prefix list; `FORBIDDEN` (whole segments: key, token, secret, password) and `PROTO` win over it. `mcpServers`, `harness.custom` and `openclaw.json` are deliberately absent: each holds a command that would later be spawned.
- Memory rules (`memory.rules()`, prefs-free, under `harness/memory-rules`) are editable by both sides — `memory_rules_write` for the agent, the **Rules** modal for the user, `DELETE …/memory/rules` to go back to `DEFAULT_RULES`. An unknown `category` on an entry is stored as given, on purpose.
- **The tool list is rebuilt on every step, not once per turn.** Only running MCP servers contribute tools, and a turn is exactly when a server starts — so a per-turn snapshot meant the agent could not use what it had just started. It did not wait: three separate turns wrote a script and spoke JSON-RPC to the listener through `shell`, which works and routes around every switch and label on the tool layer. `tools.schemas()` is an in-process registry read, so recomputing it per step is cheap, and a changed count emits a `tools` event.
- **Settings → Harnesses is one section, a group per harness** (since 2.209.0, `public/js/settings/subnav.js`, `settings/harnesses.js`): DOCA's own settings in the top row, then one Harnesses pill whose second row holds DOCA (Harness, Evaluations), OpenClaw (Skills, Snapshots, Stack, Config), OpenDots, and a pill per installed CLI harness (`cli-<id>`: launch command, model, config file, environment — the Controls ⚙ fields, same route) — each group only when that harness is installed. A new harness-specific page goes in `_SETTINGS_SUBTABS` with its `group`.
- **OpenDots is a peer harness** (since 2.208.0, `modules/harness/opendots.js`, `public/js/harness/web-stack.js`; docs/design/opendots-integration.md §3): a catalog row of kind `stack` with `surface: 'web'` whose folder and address are settings (`harness.config.opendots.{dir,url}`, default `~/opendots`, `http://127.0.0.1:4310`), so its `detect` and `installCmd` are getters. Install clones the pinned commit and copies `.env.example` (DOCA never fills its keys); its row says absent / setup required (`INTELLIGENCE_API_KEY`, `OWNER_TOKEN` empty) / stopped / answering; Start/Stop run its own Compose project `opendots` by argv (never `down -v`, never OpenClaw's `COMPOSE_DIR`); Open opens its page in a new tab, never framed under the panel. Conversations through DOCA (§4) are not built: they need its Intelligence SDK and a live instance.
- **The agent reaches what a person set up, without the person** (since 2.207.0). `mcp_connect {server, action}` starts or stops an MCP server that is already configured (never adds or edits one; in `registry.NEVER`, asked in Manual mode), and the environment names, for a stopped server, the tools it offered when last connected (`registry.lastTools`, names only, kept when it starts) — "portal: stopped, hosted by DocaDesk … when connected it offered shell, files_* ×7, screen_* ×2 … — `mcp_connect` starts it". Before, a stopped client's tools were "simply gone" and the agent's only move was to ask. `install_propose` also takes `kind: "tool"` — a row of System tools, installed with that row's own command for the OS, after a click. Shipped skills carry how: `android-app` (toolchains, the Android CLI's `--no-metrics`, a headless emulator driven with `uiautomator dump` + `input tap`, signing), `reach-another-machine` (git between machines without losing work), `check-the-panel` (every tab and section, two sizes, screenshots looked at).
- **A client tool's failure is annotated with whose machine it was about.** `mcp/tools.js::placeError()` appends one `[DOCA]` paragraph when a client-hosted tool fails with a loopback address in the text — "Cannot connect to Blender at localhost:9876" reads, from here, as a port on the DOCA host, and twice now that sent the debugging to the wrong machine. The bridge's own words are never altered (the exact string is what a user searches for) and a host-origin tool is left alone.
- **`placeBlock()` joins who asked to where a tool lands.** Both facts were already in the prompt — `clientBlock()` names the asking device, `mcp/tools.js::machineNote()` names each tool's machine — and nothing said they were related, so "look at my Blender" with a Blender on two machines had no rule behind it. The default is the asking device; the hard requirement is naming the machine when it is not theirs. Rendered only when a client-hosted server is running, since with one host there is nothing to choose between.
- **MCP timeouts are settings, and the message names them.** `McpClient.timeoutFor()` reads `mcpSettings.callTimeoutMs` / `.listTimeoutMs` from prefs (120 s / 20 s by default, ignoring anything under a second), `mcpSettings` is in `SETTABLE`, and both are listed by `settings.readable()` without needing to exist in the file first — a setting the agent cannot see is one it will never propose. The HTTP path used to surface Node's own "The operation was aborted due to timeout": no number, no owner, and no hint of the thing that matters — **the timeout stops the waiting, not the work**, so a render that outlives it still finishes and a blind retry does it twice. Both transports now say that. Note `mcpSettings` is a different key from `mcpServers`, which holds spawnable commands and stays out of reach; `sectionFor()` matches whole prefixes, so one cannot open the other.
- **Every limit names itself and says whose it is.** `modules/harness/budget.js` is the whole of it: a per-turn ledger, the `# Your limits` prompt block, and `explain()`, which turns a provider's refusal into a sentence saying whether the thing in the way is a DOCA setting (with its dotted path, so the agent can propose it) or the provider's own. Before this the only thing that stopped a long turn was a 400 rendered as four hundred characters of somebody else's JSON, which is indistinguishable from a bug. Charter rule 12 makes naming the limit standing behaviour rather than a nicety. If you add a limit, add it to `block()` and to `SETTABLE` if it lives in prefs — a limit the agent cannot name is one the user has to guess at.
- **A skill written for another harness is flagged, translated while read, and adapted only on a click** (`modules/harness/skill-audit.js`, since 2.131.0). `skills.list()` tags `harness` from a static audit of each SKILL.md (no model call — it runs per step with the manifest); `read()` prepends `readingNote()`. `adapt()` previews by default and writes only with `apply: true`, keeping `SKILL.original.md` once; shipped skills are never adapted. Tool mappings live in `TOOLS` there — add a row when a DOCA tool takes over another harness's job.
- **A conversation becomes a skill only through a person** (since 2.172.0, `modules/harness/learn.js`, TODO H10.3): `POST /api/harness/skills/draft` gives the transcript (requests, tool calls with their arguments, results, trimmed) to one `transport.ask` with only a writing prompt and returns a draft `{name, description, body}` — nothing written; the Harness side panel's "＋ skill" shows it to edit, and only `POST /api/harness/skills` (Save) writes it, refusing to replace an existing one silently. Both are `host`: a skill is instructions the agents follow. The *exactly how* of the same conversation is a recipe ("＋ last turn").
- **What a provider accepts is a contract, learned once** (`modules/harness/contracts.js`, since 2.129.0). `post()` shapes every body with `contracts.shape(body, forProvider(ep.id, model))` before sending, and the two 400 retries record what worked (`tokenField` per model, `streamUsage` per provider) in `harness/contracts`, so a quirk costs one failed request rather than one per call. Prefs `providerContracts` win over a lesson; nothing is assumed without one.
- **Cached prompt tokens are read and reported separately.** Every provider caches a stable prefix and bills a re-send at a fraction — which is the whole reason `environment.block()` keeps its volatile readings last — but each spells it differently: `prompt_cache_hit_tokens` (DeepSeek), `prompt_tokens_details.cached_tokens` (OpenAI), `cache_read_input_tokens` (Anthropic-compatible). `budget.cachedOf()` reads all three. Reading none of them is how an eleven-step turn reads as 1.6M when most of it was the same prefix arriving again at a tenth of the price. The cached count is **reported, never subtracted** — the tokens really were sent; what differs is the price — and a provider that says nothing reports `null`, not `0`, because a confident 0% for a provider that never mentioned caching is the same lie in miniature.
- **A rate limit is waited out, out loud** (`turn/rate-limit.js`, since 2.117.0). A 429 is retried on the *same* model `rateLimitRetries` times (Retry-After first, else 2 s, 4 s, …, each capped by `rateLimitMaxWaitMs`), and every wait is a `warning` event with `kind: 'rate-limit'` naming both settings. It is safe to retry because a refused request is not billed — which is exactly why a stall, which may still be billing, is not retried. A quota/billing 429 is never retried, a Retry-After beyond the cap fails at once, and a 429 never hops down the fallback chain.
- **Tokens are counted, and a guess is never printed as a measurement.** `complete()` asks for `stream_options: {include_usage: true}` and reads the trailing usage frame (it carries no `choices`, so it is read *before* the delta check that would skip it); a 400 costs one retry without the field, because counting is worth a round trip and never worth a failed turn. When a provider reports nothing the ledger estimates at ~4 chars/token and marks the whole report `estimated` — `report().source` is `provider`, `mixed` or `estimated` and clients draw the difference. Turns emit `usage` per step, `warning` once at `warnAt`%, and `compacted` when token pressure folds the transcript early.
- **A context window is found where the server reports it, and offered, never applied** (`modules/harness/context-window.js`, since 2.120.0). Each runtime's own field (vLLM, OpenRouter, Groq, Mistral, LM Studio, llama.cpp `/props`, Ollama) with `source` naming server and field; `null` when nothing said it, `reached: false` when nothing answered — never a guess from a model name. ⚙ asks on open when the box is 0 and offers "Use N"; only Save writes it.
- **Context compaction has two triggers now.** `summarizeAfter` (messages) is unchanged; `compactAt` (% of `contextWindow`) folds early via `memory.pendingFold(..., {force:true})` once the window is declared. `contextWindow` defaults to 0 = *nobody has said*, and everything percentage-based is skipped while it is 0 — deliberately, because the window cannot be discovered (`/models` does not report it and a local runtime's is whatever it was started with) and a wrong default is worse than none.
- **Nothing may cut between a tool call and its result.** Both cuts that shorten a transcript — the fold boundary in `memory.pendingFold` and the `historyTurns` cap in `memory.window` — used to be chosen by counting rows, and roughly half the rows in a working session are a call or its result. A window opening on a `tool` row is rejected outright (`Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`, HTTP 400 from DeepSeek), and because `summarizedThrough` is *persisted* while `shouldCompact` is only evaluated after a successful reply, one unlucky cut broke **every** later turn in that conversation: the turn died before the fold that would have moved the boundary could run, so the session could not heal. `memory.foldBoundary` now snaps the cut off any `tool` row (forward, so a group folds whole; backwards only when forward would leave nothing live), `window()` drops leading orphans — which is also what repairs a session whose stored boundary predates the rule — and `turn/messages.js::pairedRows` is the backstop, dropping either half of a broken pair on the way out. It matches on `c.id || c.function?.name`, the same fallback the result row was written with, or a provider that sends no call ids would have every pair read as two orphans.
- **Under pressure inside one turn, old tool results are cleared, not the turn** (`turn/clear-results.js`, since 2.124.0). When `compactReason` fires and `foldSummary` has nothing earlier to fold, `clearOld()` moves the session's forward-only `clearedThrough` so every tool result over `MIN_CHARS` except the newest `KEEP` is sent as a one-line stub; `step-request.js` applies it through `view()`. Stored rows never change, and the mark only moves forward so the prefix cache breaks once per clear, not per step.
- **Nothing may cut inside the turn in progress, either.** Both cuts are now bounded by the last `user` row. Under token pressure `pendingFold(..., {force:true})` folds only *earlier* turns and returns null when there are none; it used to fold "the older half" of the live rows, which mid-turn meant summarising the code the agent was iterating on into 250 words, and then doing it again the next step because the tool schemas alone kept the prompt over `compactTokens`. The `historyTurns` cap likewise never drops the turn's own rows: a ten-call turn is more than 24 rows, and the cap was dropping the user's request mid-turn, from rows no summary covered yet. Both triggers stay live and the lower wins; `budget.compactReason()` names which one fired, because "47688 of 1000000" in the log read as a bug when it was `compactTokens` at 40000. The ceiling this leaves: one turn larger than the model's window is refused by the provider.
- **`environment.block()` keeps its volatile readings last, under `## Right now`.** The clock, free RAM and the uptimes used to be on the first line; this block is near the front of every prompt and is rebuilt on every step, so those lines changed the prompt's opening bytes each time and destroyed the prefix that a provider's cache and a local prefill match on. New facts go above the heading, new readings below it. It is one line to undo by accident and there is a test pinning it.
- **Memory protects what has proven out, in three ways.** `locked` is the user's settled answer: `memWrite`/`memForget` refuse it for `source: 'agent'` and only `POST /api/harness/memory/:key/lock` sets it — the same shape as a settings proposal, and for the same reason. `disputed` is how the agent says a fact turned out wrong (`memory_flag`) without deleting it, because "the docs say 9876 and nothing is listening" is worth more than the silence left by a delete; a new value clears it. `history` keeps the last three overwritten values. All three reach the prompt through `memoryBlock()`, which marks locked and disputed entries inline — an unmarked entry is one the agent may freely correct.
- **`memory_rules_write` edits in place by default.** `rulesPatch()` (add/remove/replace, by rule number or exact text) changes one rule and leaves the rest; the wholesale `rulesWrite()` is still there for the Rules modal, where the user is looking at all of them. The old tool took only the complete list, which meant an agent adding one rule had to retype twenty-nine and silently deleted every one it forgot.
- `agent.preview({message})` assembles the system prompt without sending it — what `GET /api/harness/environment` does for the environment block, for the whole prompt. It is how the prompt-order and memory-marking tests assert anything at all without an inference server.
- `test/harness-awareness.test.js` covers all of this without a model: it asserts the prompt order, the refusals, that a proposal writes nothing until applied, and that a rejection with its reason reaches the next prompt.

### Manual approval (`modules/harness/approval.js`)
- **Three modes, and `auto` is the default** (`unattended` is the third, for a test bench: tools run as in auto and the agent's own proposals apply the moment they are made, audited — the owner's switch alone, with an explicit confirmation; the files that govern the agent still ask) (`harness.approval.mode`): `auto` is what this harness always did, so nothing changes for an existing install until somebody asks for it. `manual` stops each tool call that *does* something and puts a card in the transcript; the turn is genuinely blocked on the other side of it. The gate lives in `agent.js` at the call site, not inside `tools.call()`, because that is where `say()` is — the question has to reach the transcript — and because it must also cover MCP tools, which `tools.call` dispatches before it sees a definition.
- **The remembered unit is a tool plus a verb.** "Always allow `shell`" is the off switch with extra steps; `shell:git` is a thing a person can mean. `keysFor()` derives them and the card offers both, plus a plain deny.
- **A chained command is every verb in it.** `git status && rm -rf ~` leads with `git`, and a gate reading one word would wave it through on an allowlist that says nothing about `rm` — so every segment's verb must be allowed, and a command carrying `$(…)` or backticks cannot be reduced to verbs at all, so it is always asked about and the card offers no "always". There are tests for each of those shapes; they are the whole reason this is not a one-liner.
- **`FREE` is not a convenience, it is what keeps the mode readable.** Gating `system_status` and `memory_list` buys no safety and costs a question every few seconds, which is how a person learns to click Allow without reading. Anything that reads a file, runs a command, reaches the network, writes, or speaks to another machine is deliberately absent from it.
- **The mode is not proposable**, by `NEVER_SETTABLE` in `settings.js` as well as by not being under any `SETTABLE` prefix. An agent that can move itself to full auto, or add `shell:rm` to the allowlist, is filling in its own permission slip. The mutating routes also carry `requireBrowser`, the same click convention as applying a proposal — and with the same honest caveat, that it is a speed bump rather than a boundary while `shell` exists.
- **A mission is denied rather than asked.** It runs unwatched — `ask_device` is in `registry.NEVER` for that reason — so there is nobody to show a card to. The allowlist still applies, so a specialist can be given the verbs it needs in advance, on purpose.
- A question **withdraws itself** on timeout (5 min) and when the turn is stopped, and a click that lands afterwards gets a 409 the card renders as a sentence — the same rule `reach.js` follows, for the same reason. An open panel also finds questions raised anywhere else under Harness → Approvals, "Waiting for an answer".
- **The card is the record; the popup is what gets answered.** `approvalPopup()` puts the same request in front of the user, because a blocked turn whose question is three screens up in a chat nobody is scrolled to reads as a hang. It is not dismissible by clicking away or by Escape — every button on it is a decision, "denied" included — and Deny takes focus, so a stray Enter is the safe answer. One overlay at a time: a turn asks one question at a time, and a stack of modals is a worse way to say "two are waiting" than the list in the modal.
- **A turn started from a device is asked on that device too** (`askAnywhere`), through the same `reach.ask` prompt a watch already renders — no new screen, no new route, `option` choices only. First answer wins and the other copy is withdrawn (`reach.ask` takes a `signal` now). The wrist's choices come from `approval-answer.deviceChoices()` by what its owner may decide (since 2.141.0): `approve`, `always` (this kind of call — the allowlist for a host, an `approve:` grant for anyone else; never on a must-ask request), `approve_all` (when more than one waits), `deny`, and `full_auto` for a host only — all fixed ids; the device is asked only when its owner holds host or it is their own turn. Of these, `full_auto` switches the whole panel to `auto` and is a real escalation, offered because the alternative on a 450 px screen is tapping Approve forty times — which teaches a person to tap without reading — and because the only party who may turn the leash off is the user, who is exactly who is being asked. A `kind: 'agent'` client is never asked: it is not a person. This is documented on the client side in `DocaWear/AGENTS.md`, including that a still-listed prompt is an outcome view rather than a new question — the hub deliberately leaves a single target's copy alone after it answers, and re-answering the stale one is how a later request gets silently swallowed.

### The shell (`modules/shell.js`)
- **There is one place that decides what a command line is typed into**, and everything that runs one goes through it: the agent's `shell` tool, `streamCmd` (every installer), `detectBinary`, and the PTY behind the Terminal tab. Before it, all four hardcoded bash — `exec(…, {shell:'/bin/bash'})`, `spawn('bash', ['-lc'])`, `bash -lc "which …"` — so on Windows the agent's most-used tool returned `exit ENOENT` for every call it ever made. That is not degradation, it is a panel that cannot do anything.
- **A script we wrote does not run in the user's login shell.** `spec()` returns bash (`/bin/bash`, else `/bin/sh -c`) on POSIX and PowerShell on Windows; `spec({interactive: true})` is the *only* thing that reads `$SHELL`, and the Terminal tab is its only caller. v2.49.0 pointed everything at `$SHELL` and that was a regression, not a simplification: every `detectCmd` in `system-tools.js` and `catalog.js` is bash (`2>/dev/null`, `test -f x && { …; }`), so on a host whose login shell is fish or tcsh every detector and every installer broke — silently, because a detector that cannot run is indistinguishable from a thing that is not installed. `DOCA_SHELL` overrides both.
- **`run()` returns `stdout`, `stderr` and `out` separately, and a parser takes `stdout`.** `out` is the combined view and is right for a human reading a command; reading a version off it means a warning on stderr, or a login shell's banner, gets reported as the version.
- **Linux keeps bash; Windows gets PowerShell**, with `-NoProfile -NonInteractive`: a profile banner corrupts the first lines of every result, and nothing here can answer a prompt, so an interactive shell would block until the timeout with no clue why. The Terminal is the exception and keeps the profile — it is a person's prompt and their aliases belong in it. `DOCA_SHELL` overrides.
- **The flag is not `-c` everywhere.** PowerShell takes `-Command`, and Node's own `{shell}` option would hand it `/d /s /c`, which it reads as a path — so a command line goes through `execFile` with this module's argv, never through `exec`'s shell option.
- **It makes the host's shell reachable; it does not translate.** A bash command does not run in PowerShell, and a translation layer would be a third dialect that is subtly neither. Instead the agent is *told*, twice: `environment.block()` carries a `shell:` line, and the `shell` tool's own description names the syntax (both from `shell.describe()`, and both getters so they are right per host rather than per deploy). A model that thinks it has bash writes `&&` and `/` into every command and cannot tell why they fail.
- `which()` walks PATH in process, applying PATHEXT on Windows, rather than asking a login shell — which does not exist there, and which can hang on somebody's half-broken profile.
- **Two call sites were missed by the first pass and fixed on 2026-09-21**: `catalog.detect` (then `shellDetect`) and `system-tools.handleList` still ran `bash -lc`, so on Windows every harness and every system tool reported "not installed" whether it was present or not — a detector that cannot run is indistinguishable from a thing that is not there. If you add a detector, it goes through this module. The `detectCmd` *strings* in those catalogues are still POSIX and so still do not run under PowerShell; `TODO.md` ("OpenClaw is a peer, not a prerequisite") has the fix, which is for a row to declare what it looks for rather than how to look.
- **Not everything here is portable, and two are deliberately not**: `snapshots.js` spawns `bash` on the snapshot/restore *scripts*, which are `.sh` files a user supplies, and `skills.js` runs a skill's own command. Those are POSIX by nature rather than by oversight — a `.sh` file needs a shell that reads it.

### The update check (`modules/update.js`)
- **It asks `git ls-remote --tags origin` first, and the GitHub API only as a fallback.** This repo is **private**, and GitHub answers the public tags API with **404** for a private repo rather than 403 — it will not confirm the repo exists. That 404 arrived here as "no tags" and reached the user as a green "up to date", so a push genuinely never showed. `ls-remote` uses the credentials that pushed the tag, needs no PAT, and reads a private repo without trying.
- `GIT_TERMINAL_PROMPT=0` and `GIT_ASKPASS=echo` are not decoration: without them a machine whose credential helper has expired blocks waiting for a username nobody is there to type, and the check hangs instead of failing.
- A token for the API fallback is read from **`GITHUB_TOKEN`/`GH_TOKEN` in the environment only**, never prefs. `/api/prefs` is readable by every signed-in role that holds `read`, and a PAT there would be the leak `/api/mcp` had in 2.13.1.
- **"I looked and you are current" and "I could not look" are different answers.** The response carries `checked`, `source` and `reason`, `latest` is `null` rather than falling back to the local version, and the panel draws the third state in amber. A check that cannot fail visibly is not a check — there is a test asserting a failed check never reports the local version as the latest.
- Tags are chosen by **highest semver across a page**, not by whichever one the API returns first: lexically, `2.9.0` beats `2.21.0`, and the old code would have announced a downgrade as confidently as an upgrade.
- `LOCAL_VERSION` is read at require time on purpose — the process reports what it is *running*, not what is on disk — so a pull shows the old number until the server restarts, which `/api/update` already says.

### Specialist agents and missions (`modules/agents/`)
- **Off by default (`agents.enabled`), and off means the tools do not exist.** `tools.schemas()` drops `agent_dispatch`/`agent_results` when the flag is off, which is free because the list is rebuilt every step — and it is what makes rolling this back a *settings change rather than a release*, which was the requirement. There is a test asserting the tools are genuinely absent, not merely refused later.
- **A mission is a turn in its own session, wrapped so nobody waits for it.** It cannot be a nested turn: `_running` allows one turn per conversation, so the orchestrator would be blocked for the mission's whole duration, and the entire point is that the user keeps talking. `dispatch()` creates a session, calls `agent.turn()` **without awaiting it**, and returns an id.
- **Specialists are deliberately smaller, and that is the whole reason they exist.** A sub-agent inheriting the orchestrator's prompt costs it on every step of every mission. A profile narrows: its own short role, its own tool allowlist, `memory: false` by default, and `environmentBrief()` instead of the full environment block. There is a test pinning that a specialist prompt is *shorter* than the orchestrator's — invisible in review, one careless edit from being false.
- **Three limits are structural, not configurable.** The charter is prepended to every sub-agent prompt and a definition cannot drop it. Sub-agents **report, they do not propose** — `settings_propose` and `install_propose` are in `registry.NEVER` and stripped at normalize time, so proposals keep one owner. And **no recursion**: `agent_dispatch` is in `NEVER` too. Depth one is where the cost of a mission stays a number somebody can predict.
- **A profile overrides only what it names.** Temperature, history, the summariser and the rest stay the panel's settings, so a specialist never acquires a second set of defaults to maintain.
- **Mission state is one document per mission plus a small index** (`agents/missions`). Not one file for all of them — that rewrites the whole file per update and lets two running missions race a read-modify-write, the exact disease `store.js` exists to avoid. Not one per agent either: a mission belongs to the mission, the roster is user-editable, and deleting an agent must not delete the history of what it did. The index is what a progress bar renders from; live progress rides the event stream, the same ephemeral/durable split used everywhere else.
- Definitions are JSON files in `AGENTS_DIR` (a managed path), one per agent, with the shipped ones in code as a fallback so a fresh install has them without the directory existing. A file wins over a built-in of the same id, and deleting the file reverts rather than removes. Files are writable by the agent itself — that is how a new specialist gets built.
- **The panel edits a definition as JSON, not as a form.** The fields are few, they are documented in `registry.js`, and a form would need rewriting every time one is added — while the agent writes these files with no form at all. The modal says which three tools can never be granted, and `save()` reports `refusedTools` so the panel can say what it removed rather than storing something quietly different from what was typed.
- **The missions bar polls, and stops polling.** It is a status light rather than a transcript — the transcript belongs to a conversation nobody has open — so it refreshes every 3 s *while something is running* and clears its timer when nothing is. A timer that outlives the thing it was watching is how a quiet panel ends up making a request a second for the rest of the day.
- **A restart pauses a mission; it does not fail it, and it does not resume it.** The turn was a promise in a dead process, so without `missions.recover()` (called once when the server starts listening) the row said `running` forever and the bar above never stopped polling. `paused` keeps the work, because the mission's session still holds every step. Whether to finish is the user's call: `missions.block()` tells the orchestrator to open its next reply, from whichever device writes first, with a one-line account (what, how far, what it cost) and one short question, and `agent_resume({mission, continue})` carries out the answer. A yes resumes **in the same session**, so the specialist reads what it did instead of starting over; a no marks it `cancelled`. `agent_resume` is in `registry.NEVER`: a specialist does not answer for the user.
- **Stopped work waits for its person** (since 2.243.0, `harness/stopped-work.js`): a work chat whose job is `stopped` is listed to the Orchestrator (`# Stopped work`, appended to its missions block), which says so once and asks restart or drop; `work_chats {action: restart | drop}` carries out the answer, and the Harness bar shows the same rows with ↻ Restart and Drop (`POST /api/harness/work/:id/restart|drop`). `dropped` ends a job without waking anyone.
- **Stop means stop, and it is visible** (since 2.242.0, audit 2026-10-06; `agents/stopping.js`, `supervisor.missionStopped`): a running specialist has ■ Stop in the missions bar (`POST /api/harness/missions/:id/stop`), and a person's Stop ends that line of work — the work chat that sent it is set `stopped` (with `stoppedWhy`) instead of being woken with its results, a stopped work chat stops the specialists it sent, and the Orchestrator is not woken for reports right after its own Stop. What works on its own is listed beside the missions with why it started (`supervisor.autoNow`, `GET /api/harness/working`) and its own Stop. Putting finished work away (`missions.archive`) announces quietly: devices take the row off, nobody is notified, no computer timer starts. ### Product names (`modules/branding.js`)
- **Every name a person reads comes from one file**, because the panel will be sold under a customer's label and under whatever the public release is called, and a rename that means grepping forty files is a rename that does not happen. Overrides live in prefs under `branding`, so a private label is a settings change; the UI for it is deliberately absent until it can sit behind the admin password, since the only thing worse than the wrong name is one an agent changed.
- **The distinction that matters is branding vs identifier, and getting it wrong breaks installs.** `~/.openclaw/` and `openclaw.json` are paths that already exist on disk; `openclaw-panel.service` is a unit somebody enabled; the `openclaw` row in `catalog.js` is a real third-party product, not our label; `openclaw-dashboard` in package.json is an npm identifier; `DOCA_DATA_DIR`, the `doca` harness id and the `med_`/`job_`/`trn_` prefixes are identifiers too. **None of those are renameable.** The test: if changing the string would stop an existing machine working, it is not branding. There is a test pinning it.
- The front end fills `data-brand`, `data-brand-title` and `data-brand-text` from `GET /api/branding` at boot, and the HTML ships with the default name already in it — so a failed fetch reads correctly instead of leaving empty boxes where the product should be.

### Install proposals (`modules/harness/installs.js`)
- **The agent never supplies a command.** It picks a `kind` and an `id` from a catalog this file owns — an Ollama model, one of `services.js`'s inference services, a harness from `catalog.js` — and `apply()` invokes the panel's *existing* installer through `jobs.invokeHandler`, the same handler the Models / Services / Harness tabs call. An install proposal therefore cannot run anything a button in this panel could not already run, and there is no path from a sentence the model wrote to a shell. That, not "the user approved it", is the safety property. Keep it.
- It exists because the alternative is worse, not because installing is dangerous: the agent can already install with `shell`, and a hand-written `docker run` gets the image, ports, GPU flags and HF cache mount subtly wrong, leaving something that looks installed and does not work. The services catalog knows all of that. Charter rule 6 routes installs here and says not to use `shell` for what this covers.
- Model names are free text on purpose — nobody can enumerate Ollama's library — but they are validated to `[\\w.:/-]` and go to Ollama's `/api/pull` as JSON, never as a shell word. Services and harnesses must exist in their catalogs, and the refusal **lists what does exist**, because a dead end is worse than a no.
- `apply()` re-validates, for the same reason `settings.apply()` re-runs `refuse()`: the request comes from a browser and the stored file could have been edited in between.
- **Declined rows stay in the prompt with their reason** (`block()`), and say not to ask again. An agent that cannot see it was told no asks again, and being asked the same question twice is how a person learns to stop reading the questions.
- Installs and settings changes share one tray in the Harness tab. They are the same question — something only the user may do — and two lists would mean two places to look for an unanswered one.

### Nobody waits for a working conversation (since 2.148.0, decided with Al 2026-10-04)
- **A message to a conversation that is working is never refused** (`modules/harness/inbox.js`). `agent.send()` is the entry point everything uses — the panel's console and Projects chat (`/api/harness/chat`), the floating chat (`/api/chat`), `/api/v1` devices, a task handed to a busy work chat, a plan approval: a free conversation gets a turn, a working one keeps the message in its inbox. The running turn reads every waiting message **before its next step** as an ordinary user row (`user_added` event), so the agent sees it, answers it and changes course — one transcript, never interleaved; what is still waiting when the turn ends starts the next turn at once, as whoever wrote it. A device gets `202 {queued: true}` and its `turnId` goes `started` → `done` with the answer of the turn that read it (`onAnswer`). In memory, like the turns: a restart drops what was waiting. The SSE side is `send-stream.js` (`queued`, then `queued_read` or `queued_started` and the turn), and the browser side `agent-ui/queued-send.js`.
- **The Orchestrator stays free by code** (`turn/handoff.js`): after `orchestratorWorkSteps` (default 3) steps of real work in its own turn — anything `isWork()`: not reading, not memory, not coordinating — the next step that wants more does not run. Its calls get result rows ("not run here"), a work chat is created with the request, what was done and what was next, and the Orchestrator ends its turn with one line. Its prompt says so too, but the prompt alone had twice let it do a 10–28-step job while the person waited.

### The face (since 2.161.0, `modules/face`, `public/js/face`; hive.md §5)
- **One state for the hive, made from events that already exist** (`face/state.js`): a turn's `agent.events` (`session`/`thinking` → thinking, `text` → speaking, `tool_call` → working with the tool as detail, `approval` asked → asking), pending approvals, and which conversations `lifecycle.running` still holds (a turn that left it is idle, or briefly `error` if its session failed). - **The renderer is a canvas of dots driven by a JSON spec** (`FACE_DEFAULT`: palette from protolab.tech, dot count, eye and mouth geometry, HUD, grain, per-state overrides in `FACE_STATES`) — noise when idle, a face when attending. `/face` is the kiosk page (F for full screen, keeps the screen awake); **assistant mode** (since 2.214.0, `public/js/face/assistant.js`): tapping the corner face — or the wake word — opens the face full screen and starts a live call that answers aloud with no chat (`chatToggleCall({assistant: true})`, the face driven by the call's voice whatever `faceVoice` says); after `call.assistantIdleSec` of quiet, a screen listening for its wake word ends the call and waits for the name, otherwise the call keeps listening; ✕ or Back closes it. Assistant mode's quiet counts exchanges, never mere sound. **Concepts on the face** (2.215.0, `face/concept-engine.js`, data in `face/concepts/*.js` as `FACE_CONCEPTS`: a glyph, a meaningful colour, words in English and Italian): as a spoken sentence starts, a concept it names gathers the dots into the glyph's silhouette (drawn on a hidden canvas, sampled on an even grid) in its colour, then they flow back; `face.shape()`. The default form (2.216.0, `face/poly.js`, `spec.form: 'poly'`; `'face'` keeps eyes and mouth) is a polyhedron drawn by points along its edges, turning in 3D with perspective, breathing, and morphing every ~12 s through tetrahedron, cube, octahedron and icosahedron; the states set its spin, breath, scale and colour, and the voice's level swells it. Each point is a 128 px sprite with a peaked profile — a small near-white core over a faint glow as wide as before — drawn at the screen's own density (up to 3×), with no scanlines by default (2.216.1); a concept holds 2.6–4.5 s. The face's motion is a spring with constant drift (no snapping), and the corner face has no ring — its edge fades out by a radial mask. A screen's voice is matched to the speech service's own list (`modules/tts-voices.js`: "Heart" → af_heart, an unknown one falls back to the hive's with `X-Doca-Voice-Fallback`; `GET /api/chat/voices`, a dropdown in Settings → Voice). The face can sit in the panel's corner per screen (Settings → General → Appearance, kept in the browser until device pages, H2.4) — its own circle beside the chat button since 2.199.0, opening `/face`; drawn inside the button it hid the chat's open/close. A screen's spec is `faceSpec()`: the screen-home setting `face.spec` (an edition carries one, since 2.184.0) under the browser's own `localStorage['doca.face.spec']`.

### Recipes: what worked, run again without the thinking (since 2.159.0, `modules/recipes`)
- **A recipe is tool calls with `{parameters}` and checks**, one JSON file per recipe under `DOCA_DATA_DIR/recipes` (earlier revisions under `recipes/previous`). It is made from a turn that worked (`store.fromTurn`: the last turn's calls that did not fail, with literal values lifted into parameters — `POST /api/recipes/from-session`, the agent's `recipe save_last`, or "＋ last turn" in the Harness side panel) or written out (`recipe save`).
- **A run uses no model and no new gate.** `recipes/run.js` makes a conversation of its own and feeds each step to the turn's own `runToolCalls`, so the conversation's mode, the person's level and grants, approvals (`askAnywhere`, so a phone is asked too) and the charter's tool rules are exactly the agent's; a step whose result is an error, a refusal, a non-zero `exit` or fails its `check` (`contains` / `matches`) stops the run and says which step. A value landing in a `shell` step is quoted for the host's shell once (a placeholder the author already quoted is replaced quotes and all). The supervisor leaves the run's conversation alone (it has no job).
- **`recipe` is in `registry.NEVER`**: a run asks for approvals as a person's turn does, which a mission must never do; its leader runs recipes. Reading and running is the `chat` right, as the person; deleting a recipe the hive shares is `host`.
- **A skill names its recipes** (since 2.173.0, TODO H3.5): `recipes: [id, …]` in a SKILL.md's front matter is listed under the skill's body when it is read (`skills.recipesNote`) — the skill says when and why, the recipe exactly how — and a pack carrying the skill carries those recipes. A named recipe not saved here yet is listed as missing.
- **[IO]**: `GET /api/recipes/:id/export?format=json|bash|powershell` — a shell-only recipe becomes a script per OS with its parameters as arguments (what an Agent Skills folder keeps under `scripts/`); one with other tools has no faithful script form and says so (409).

### Schedules (since 2.162.0, `modules/schedules`)
- **A turn or a recipe on a timetable, as its person** — `every` N minutes or a five-field cron expression in host time (`schedules/when.js`; Sunday is 0 or 7). A due schedule's `nextAt` moves on before it runs, so a slow run never fires twice; a turn goes through `agent.send()` into the schedule's own conversation (claimed by the person, so it is theirs and their devices hear it), a recipe through `recipes/run.js`. Both act with the person's level and approvals; a person gone or suspended pauses it. The ticker starts in `boot.afterListen`.
- **The agent proposes, a person switches on.** The `schedule` tool creates schedules in state `proposed`, which never fire; only the panel (`POST /api/schedules/:id/state`, Harness → Schedules ▶) turns one on. The tool may list, pause and delete, never resume. It is in `registry.NEVER`. A person sees and changes their own schedules, a host every one.

### Packs (since 2.163.0, `modules/packs`; hive.md §2.4, §9)
- **A `.dpack` is a zip whose parts are each in their own world's format**: `pack.json` (contents and needs: DOCA version, tools, secrets to fill), `skills/<name>/` Agent Skills folders, `agents/<id>.md` subagent markdown, `recipes/<id>.recipe.json` (+ `.sh`/`.ps1` when shell-only), `mcp.json` as `{mcpServers}`, `memory.jsonl`, `AGENTS.md` for the memory rules. - **Nothing secret travels**: an MCP server's env/header values with secret-shaped names are emptied and listed in `needs.secrets`; a client-hosted server is left out (its address means nothing elsewhere).
- **Import is a dry run, then a choice** (`POST /api/packs/plan`, then `/api/packs/import` with `only` and `overwrite`): what it adds, what exists here, the command each MCP server would run, what it needs, what it skipped and why. Every write goes through the owning module (skills `importFrom` with its name check, `registry.save` with NEVER, `recipes.store.save`, `mcp.registry.upsert` switched off, `memWrite`, `rulesPatch` adding only new rules). ### Traces: what each turn did (since 2.182.0, `modules/harness/trace.js`; TODO H10.1)
- **A span per model request and per tool call, tied to the turn's run** (`trace_spans` in doca.db, schema step 8; runs.js is the run). ### Retrieval: finding by meaning (since 2.181.0, `modules/retrieval`; TODO H10.2, an experiment)
- **Behind `experiments.retrieval` and inert without `retrieval.model`** (docs/experiments/retrieval.md). When on, `memory_search` and `recall_conversations`' search merge the keyword ranking they always had with one by meaning, by reciprocal rank (`retrieval/sources.js`), over exactly what the keyword search may see — memory, and the conversations the person may open — so it can never find what a person could not. A failed embedding call returns the keyword result with a line saying so.
- **Embeddings come from the owner's provider** (`retrieval/embed.js`: the OpenAI-compatible `/embeddings` of `retrieval.provider`, Ollama by default) and live in doca.db (`embeddings`, schema step 7: a row per piece and model, the vector as base64 float32 in a TEXT column both databases take). `refresh()` hashes each piece (≈1200 characters, overlapping) and embeds only what changed; ranking is a scan in process — pgvector with PostgreSQL is where it goes past a few hundred thousand pieces. Settings → Harness → Retrieval sets the model, tries it on memory and empties the index (`/api/retrieval*`: reading is `read`, the rest `host`). `npm run experiment -- retrieval` measures it (each experiment's measurement is `bin/experiments/<id>.js`). `test/retrieval.test.js` uses a stub that maps words to concepts.
- The prompt's own memory block still matches by keyword: it is assembled synchronously on every step and must stay cheap.

### Stopping a turn, and what a prompt is made of
- **A turn belongs to the user, not to the device that started it.** `_running` holds `{turnId, ctrl, by, startedAt}` per session, and `POST /api/v1/harness/turns/:id/cancel` (by turn id *or* session id) aborts it for any device with `harness:chat`. The phone that began a runaway turn may be in a pocket; the person watching it burn tokens is at the dashboard.
- **Stopping is not failing.** The turn ends on the bus as `agent.turn` state `cancelled`, never `failed` — a client that draws a deliberate stop in red teaches the user that pressing Stop broke something.
- **Stop means the next step, and the message says so.** Abort cancels the request in flight; it does not unmake the one the provider already accepted. The tokens already spent stay spent. This is the same honesty the MCP timeout message needed ("it stopped the waiting, not the work") and for the same reason.
- In the panel, Stop is not a message we send: `sseStream` takes a `signal` now, and every SSE handler that drives a turn already ties `res.on('close')` to that turn's `AbortController`, so hanging up *is* the stop. `AbortError` is swallowed in `sseStream` rather than drawn, or every Stop paints a red error under the answer it just stopped.
- **`GET /api/harness/prompt` says where the tokens are** (`agent.breakdown()`): every prompt section, the tool schemas **by owning MCP server**, and the transcript, plus `perStep` and `worstCase = perStep × maxSteps`. It exists because percentage-of-window warnings answer "will it fit" and say nothing about cost: a turn re-sends the whole prompt on *every* step, and the first screenshot through this harness cost 1.6M tokens over eleven steps while the context never passed 155k — 15% of a million-token window, which reads as perfectly fine. A bare install is ~4k per step, so anything much above that is memory entries, MCP tool schemas or transcript, and the byOwner breakdown is what makes it actionable: a fat server can be switched off on the tools list.

### Attachments (`/api/attachments`)
- **An attachment is a file, and what the model gets is a path.** `modules/attachments.js` writes the bytes into `ATTACHMENTS_DIR` and the turn carries `[{name, path, bytes, mime}]`; `turn/messages.js::toApiMessages()` renders `attachments.note()` onto the message the model reads. The point of the shape is that it makes **vision optional instead of load-bearing**: a path costs ~20 tokens whether it names a 2 KB CSV or a 40 MB STEP file, `read_file`/`list_dir`/`shell` already work on it, "put that one in X" is a tool call rather than a feature, and a bwkl, a log or a zip is the same thing to this code as a photo. Do not "upgrade" it into image content blocks; when there is a vision model, that becomes one optional thing done *to* a file that already exists.
- **It is not `modules/api-v1/media.js` and must not merge with it.** Media expires, is mode 0600, is addressed by a `med_` id and lives outside the workspace — all four deliberate. A device still uploads to media, and `api-v1/harness.js::post()` then copies the bytes into the attachments directory, because a reference the agent is forbidden to read is not a reference (charter rule 8). That copy is what the `FUTURE(phase 2)` refusal on `mediaId` turned into; an id that was never uploaded is now a **404**, not a silent no-op, because the device believes it sent something.
- **`ATTACHMENTS_DIR` is a managed path**, so it shows in Settings → Paths, is proposable (the `paths` prefix is in `settings.SETTABLE`), and — the reason it is registered rather than hardcoded — `paths.describe()` feeds `environment.block()`, so the agent is told where attachments live as a standing fact instead of a sentence somebody has to remember to add. `attachments.dir()` re-resolves through `describe()` on every call rather than trusting the boot constant, for the same reason every other path-using module does.
- **The directory is the index.** `list()` reads the filesystem and merges the JSON sidecar where there is one, so a file dropped in from a file manager is an attachment — keep that. The sidecar only holds what the filesystem cannot say (which device sent it, the name before it was made safe). `safeName()` strips separators, control characters and leading dots; `uniqueName()` makes `report-2.pdf` rather than overwriting somebody's `report.pdf`. There are tests pinning both.
- The 50 MB cap is on the **upload**, matching multer in `server.js`, and the refusal says the escape hatch out loud: put the file in the directory yourself and name it. Do not raise the cap to make a big file work — that is what the directory is for.
- **A panel test's DOM stub is a claim about the browser, and it has been wrong twice.** `markdown.test.js`'s stub had no `lastElementChild`, which is exactly what `mdListEl` tests before opening a nested list — so under test every nested list rendered flat and that branch had never run, while the panel drew something else (bullets came out numbered). `fold-runs.test.js` then needed `appendChild` to *detach* a node from its previous parent and `replaceWith` to clear it, or rows moved into a collapsed row stayed in both places and a transcript grew where it should shrink. The rule both times: when a stub cannot express what the real DOM does, a green test pins a shape nobody sees. Add the property to the stub, and check the feature in a browser once — the browser is where the other half of a UI lives.
- **A document is a fourth kind of media, and it opens rather than draws.** `attachments.playableKind` returns `doc` for markdown and plain text, so a plan travels the road a picture already had - copied into attachments, kept with the conversation, addressed by name, carried on `images[]` with its `kind` - and only what the client does with it differs. The panel draws a row that opens a window rendering it with the same markdown renderer the transcript uses; a phone should offer the choice (open it, or carry on in the chat); a watch should not try to show a document at all, which is what the `kind` is for. This widened what `harness:chat` can fetch to the kinds a conversation puts in front of a person; everything else in the attachments folder is still a 404 on that route.
- **Presence is the panel saying it is being looked at** (`modules/presence.js`, since 2.123.0). `public/js/lib/presence.js` posts `{visible}` every 30 s while the page is visible and once on hide; `presence.line()` goes into the per-step readings (`liveBlock`, after the history, never the cached prefix). In memory by design, never inferred from sockets. Since 2.127.0 the hub's *own* pushes (automatic Orchestrator replies, mission and work-chat start/finish) carry `quiet: true` from `presence.quietFlag()` while somebody reads the panel — PROTOCOL §11.4: update, do not notify — and `wake.js` sends no `device.wake` for a quiet event. Never on a turn a device asked for. The clients' half is on the portal list.
- **A stuck job gets one try on a stronger model, if one is named** (`modules/harness/escalate.js`, since 2.119.0). The supervisor's two "stuck" verdicts — a failure loop and idle turns — call `tryEscalate()` before blocking: it sets the conversation's `modelChoice` to `escalateTo`, marks `job.escalated`, reports progress upward (no wake) and wakes the job with a "look again from the start" message. Once per job; `autoTurnsPerJob` running out is never escalated. `escalateTo` defaults to `null` and is drawn as a rung in ⚙ (`public/js/harness/escalate.js`), so it is listed beside `fallbackChain` in the has-a-box test.
- **A proposed plan is a document put in front of the person** (`modules/harness/plan-doc.js`, since 2.118.0). `work_plan propose` saves the revision as `plan-rN.md` and shows it on the `doc` road — a window with Approve/Reject in the panel (opened by itself when fresh), the phone's existing open-or-carry-on choice, nothing on a watch — so no `/api/v1` field was added. The `plan` field on the media record is the panel's; `imageView()` does not send it to devices. Only the user's route decides a plan; the tool result tells the agent to stop and wait. **Approve starts the work** (since 2.126.0, decided 2026-10-04): `handlePlan` calls `organization.carryOut()`, which sends "carry it out" to the proposing conversation as the dashboard client, never interrupting a turn already running there.
- **The agent shows media with `show_media` (`show_image` is its old name, kept as an alias).** Images are drawn, audio and video get a `<controls>` player, and the list is the one the Files tab previews with, so a file that plays when clicked there plays when the agent sends it here. `attachments.playableKind()` decides which of the three it is, server-side, and the `kind` travels on the record — a client never parses a mime type. Caps differ because the things differ: 20 MB for a still, 200 MB for a clip. `res.sendFile` answers the byte ranges a player asks for while seeking, which is why playback works without a route of its own.
- **A voice message is an attachment plus two facts.** 🎤 in the floating chat records with `MediaRecorder`, uploads the recording as an ordinary attachment, transcribes it through the STT the call mode already uses (`POST /api/chat/transcribe`), and sends the transcript as the message. The recording rides along, because a transcript is a guess about what was said. The turn then carries a bracketed note telling the agent it was spoken and to answer as if speaking, and the reply is read back through `POST /api/chat/synthesize`. Both halves are needed: the note is what stops a spoken question being answered with three screens of prose, and the speaking is the panel's job rather than the model's. 📷 is `<input type="file" accept="image/*" capture="environment">` — the native camera, no preview and no permission of our own to manage.
- **The agent shows a picture with `show_media` (alias `show_image`), never with markdown.** The tool copies the file into attachments (so a later edit to the file cannot change what was shown), emits an `image` event *before* the Result fold, and keeps `images` on the tool row so a reload draws the same sequence; the model reads only the result line. Both chats render it with `agentImageEl()` (`agent-ui/media.js`), built from elements and always pointing at `/api/attachments/:name` — a chat that draws `![](url)` fetches whatever address a prompt injection talked the model into writing, which sends the conversation to somebody else's server. png, jpeg, webp, gif, avif and svg (`attachments.IMAGE_MIME`), 20 MB. Served with `nosniff` and a sandboxing CSP because an SVG opened in its own tab is a document that can run script. Devices get `images[]` on `agent.turn` done and in transcripts, fetched from `GET /api/v1/harness/images/:name` under `harness:chat` — images only, so that scope does not read every attachment. No `loading="lazy"` on these: a lazy image in a shrink-to-fit bubble has no size, so the floating chat never fetched it.
- Only the built-in harness understands attachments. **Another default harness is asked the way it says it can be** (since 2.201.0, `modules/harness/one-shot.js`, TODO H11.1 — kept and made adapters rather than retired): OpenClaw through its gateway (openclaw.json's chat completions endpoint), a CLI through its own one-question mode, the catalog row's `oneShot` argv (`claude -p`, `codex exec`, `gemini -p`, `copilot -p`, `cursor-agent -p`, `amp -x`, `qwen -p`, `opencode run`, `crush run`, `goose run -t`, `cn -p`) — spawned with no shell, the message one argument, in the workspace, stdin closed. A harness with neither says so and points at the Harness tab; nothing silently falls back to a different agent any more (it used to be the gateway, else `claude -p`, whichever harness was the default). These are other people's agents acting on this machine with their own permissions, so only a host's floating chat reaches them. They get the message alone, which is why the composer should keep saying so rather than dropping files quietly.

### Logs (`/api/logs`)
- **One source per harness, and the three kinds are not equally served.** `modules/logs.js` is the registry. `builtin` is a *subscriber*, not a reader: the DOCA harness has no process and no file, but every turn already emits `session` / `tools` / `usage` / `warning` / `tool_call` / `tool_result` / `proposal` / `compacted`, so `agent.events` (a module-level emitter that `say()` publishes to alongside the caller's `emit`) is the stream. `stack` is `docker compose logs --follow`, which is all this route used to be. `cli` **has nothing to follow** — a terminal harness is launched by the *browser* typing into a PTY (`public/js/harness-console/external.js` → `modules/terminal.js`), so the server never sees lines, only bytes belonging to one tab, and they end with the tab. It is listed as unavailable with that reason rather than hidden or offered as a stream that never speaks; making it real means DOCA owning the launch, which is a different job.
- **A line is an object — `{ts, source, label, level, text}` — and the level is decided server-side.** The old shape was a bare string that the browser scanned in full for the word "error" to pick a colour, which cannot survive a source tag: one harness named "error-handler" would paint every line it wrote red. `levelOf()` is the fallback for text sources only, applied to the text and never to the tag. The client still accepts a bare string, so a cached copy of `logs.js` against a newer server degrades instead of printing `[object Object]`.
- **Tool arguments are logged by parameter name, never by value.** `/api/logs` is readable by every signed-in role that holds `read` — the reach that once made `GET /api/mcp` leak bearer tokens — and an argument is exactly where a key or a password sits. The names answer "which tool, called how"; the values stay in the transcript behind the panel. There is a test pinning this. `text` deltas are dropped entirely: one line per token is the conversation retyped badly.
- **Source colours come from a palette with no red and no amber in it** (`public/css/logs.css`), assigned by position in the sorted id list so a source keeps its colour across a reconnect. Red is error and amber is warning, and a source wearing either is a line you have to read twice.
- The ring buffer in `logs.js` subscribes at require time on purpose — the harness works whether or not the tab is open, and a log you can only see if you were already watching is not much of a log. It starts no process and writes no file, which is why it does not belong behind the listen path the way `registry.startAutostart()` does.

### MCP servers (`/api/mcp/*`)
- `modules/mcp/` is self-contained: `client.js` is a hand-rolled JSON-RPC 2.0 client (newline-delimited JSON over a child process's stdio, or POST for an HTTP server), `registry.js` holds the definitions in prefs under `mcpServers` plus the live clients, `tools.js` presents running servers' tools to the harness, `export.js` writes them into other agents' config files. **Do not add the official MCP SDK** — it is ESM and this project is CommonJS with seven dependencies that all pull their weight.
- **The Hugging Face token is in the protected keys** (since 2.240.0, `modules/hf-token.js`, `DATA_DIR/keys/huggingface.json`, 0600, PROTECTED_FILES): `loadModelsPrefs()` puts it back into `models.hf.token` for its readers and `saveModelsPrefs()` takes it out; migration `2.240-hf-token` moves an older file's.
- **The same holds for prefs (`modules/secrets-mask.js`, since 2.147.1):** `GET /api/prefs`, `/api/models/settings` and `/api/models/hf/settings` are readable with `read` and handed out the HuggingFace token in clear; secret-named values and every MCP `env`/`headers` value now read as `MASK`, and a `MASK` posted back means unchanged. A new secret in prefs needs a secret-shaped name (`…token`, `…key`, `…secret`, `…password`) or it will be read out.
- **The agent's file tools read the settings file with its secrets masked** (since 2.245.2, `modules/harness/secret-view.js`, audit 2026-10-06 coh F1): the keys files are refused outright, but the prefs file still holds a channel's token and MCP `env`/`headers` — so it, its `.bak`, the migrations' and checkpoints' copies, write_file's backups of it, OpenClaw's config and any `.env` (not `.env.example`) read through `read_file`/canvas with every secret-named value as `MASK`; `search_files` leaves them out and says so; `http_fetch` never uploads one; `write_file` refuses content carrying `MASK` into one (dots written back would replace the real secret). `shell` can still `cat` them — the stated limit of one account.
- **Secrets are masked on the way out of the registry, and unmasked on the way back in.** `status()` replaces every `env` and `headers` *value* with `MASK`, keeping the names; `normalize()` and `updateFromDevice()` treat an incoming `MASK` as "unchanged". Both halves are required: `GET /api/mcp` is readable by every role that holds `read` (it had no auth at all when this was written), so any tailnet peer could read a client-hosted server's bearer token and a stdio server's env — and the dashboard form reads `env` straight back into a textarea and posts it on save, so masking without unmasking would write dots over the real token the first time somebody renamed a server. The live client is built from `get()` and `export.js` reads `load()`, both raw, so nothing masked reaches a connection or an exported config. This was found because the agent curled the panel to work around a stale tool list and the token came back in the listing — `environment.js` had been careful about exactly these two fields all along, and that care was worth nothing while another route gave them away.
- **Where a tool lands is a fact the agent has to be given, not one it can infer.** A server is either on the DOCA host (same filesystem, processes and `localhost` as `shell`) or hosted by a paired client (another machine, its own `localhost`, invisible to `shell`, gone when that machine sleeps). `environment.block()` labels every row with which, and adds the three-bullet explainer **only when both kinds are present**; `mcp/tools.js::machineNote()` repeats the short version per tool, but only once any client tool exists, because it is a prompt rebuilt on every step. A name with two segments after the server id (`mcp__<client>__<their-server>__<tool>`) is a server that machine hosts in turn. This is the distinction that costs an hour of debugging when it is missing: "Blender on `localhost:9876`" means a different machine's 9876 depending on which server you asked.
- Tools reach the model as `mcp__<server>__<tool>` (OpenAI function names allow only `[A-Za-z0-9_-]`, max 64 chars, hence the slugging in `registry.slug()`), and `modules/harness/tools.js` merges them into `describe()`/`schemas()`/`call()`. **Only servers in state `running` contribute tools**, which makes the harness tool list dynamic — that is why `_harnessLoadMeta(true)` re-fetches when the ⚙ panel opens, and why `_harnessDisabledTools()` starts from the saved list instead of reading absent checkboxes as unticked.
- Nothing is started implicitly. `registry.startAutostart()` is called from the **listen path** in `server.js`, never from `createApp()`, so requiring the app (as every test does) cannot spawn somebody's child processes.
- A server that fails to start answers **200 with `ok: false`** and its stderr in `/api/mcp/:id/log`, because the panel wants to draw that, not catch it. Unknown *servers* are still 404.
- **A catalogue of servers the panel knows how to add** (since 2.158.0, `mcp/catalog.js`; MCP tab → "From the catalogue"): Playwright (a headless browser driven by accessibility refs) and Chrome DevTools, each a fixed command with an optional one-time `setup` (Playwright's `install-browser`) run before it is added, off until started. The agent asks with `install_propose {kind: "mcp", id}` and never supplies a command — the same property the other install kinds keep. A test stands in for `catalog.setup` so no suite downloads a browser.
- **A stdio command that is a `.cmd`/`.bat` runs through `cmd.exe` on Windows** (`mcp/spawn-spec.js`): `npx` is `npx.cmd` there and Node refuses to spawn a batch file without a shell, so until 2.158.0 every `npx`/`uvx` server failed to start on a Windows host.
- Tests use `test/fixtures/mcp-stub-server.js`, a real stdio MCP server; `--fail` makes it exit at once to exercise the failure path. No network, no installed server needed.

### Virtual machines (`/api/vms`)
- `modules/vms.js` shells out to `virsh` and `VBoxManage`. Both are optional and **neither is installed by default** — each hypervisor is reported separately with its own `available`/`error`, and "not found" is the expected state, not a bug.
- Commands run through `execFile` with an **argv array and no shell**, with `LC_ALL=C` because the state words are parsed. A VM name from the client is checked against the machines that exist before it is used, so it cannot arrive as a flag (`--all`). Do not switch this to a shell string the way `modules/docker.js` does.
- **Hyper-V, UTM and Parallels sit beside them** (since 2.175.0, `modules/vms-desktop.js`, TODO H1.7): rows of the same `HYPERVISORS` table that bring their own `present()` (Hyper-V is a PowerShell module, not a binary with `--version`), `list()` and `act(action, name)`; a VM's name reaches PowerShell as `$env:DOCA_VM`, never spliced into the script. A row that cannot exist on this OS (Hyper-V off Windows, UTM and Parallels off a Mac) is left out of the list rather than reported missing. The parsers are tested against samples in each tool's documented shape: none of the three has run here.
- An empty libvirt list is almost always the connection URI (`virsh` defaults to `qemu:///session`, virt-manager's machines are usually in `qemu:///system`); it is settable and stored in prefs under `vms.libvirtUri`.
- The parsers (`parseVirshList`, `parseVboxList`, `parseVboxDisplay`, `normalizeState`) are exported and tested against captured real CLI output, which is how this is covered without a hypervisor.

### Models (`/api/models/*`)
- **Every local model server, whoever started it** (since 2.241.0, `modules/model-servers.js`, `GET /api/models/servers`, the sidebar's ◆ Model servers): each local provider is asked in its own dialect — a llama.cpp router's `/models` (loaded, sleeping, unloaded; a loaded model's own server's `/slots` says it is generating), a llama-server's `/slots`, Ollama's `/api/ps`, else `/models` — and joined with **DOCA's own requests in flight** (`harness/inflight.js`, filled by `transport.complete()` with what made each: a step, a fold, an ask, a probe). Generating with none of DOCA's in flight reads "for something else on this machine — not DOCA". Asked only by the sidebar while a page is visible: never from `/api/status`, which a device's sampler reads in the background.
- **Five modules, one tab**: `models.js` (settings, the non-LLM tool catalogue, the storage strip), `models-ollama.js`, `models-hf.js`, `models-local.js` (non-LLM model files) and `models-llamacpp.js` (managed `llama-server` processes). None of the backends they talk to is installed by default — "Cannot reach Ollama", "llama-server missing" and an empty tools list are correct first-run states, not failures.
- **Nothing here may assume a POSIX box.** This section was written against one Linux machine and every shell-shaped assumption in it was silently false on the Windows host the panel is actually tested on: `df`/`du` for the storage strip (every figure drew "—"), `bash -lc` for HuggingFace detection (a working `huggingface_hub` reported as absent), `python3` as the interpreter's name, and a `PATH` joined with `:` — which does not merely fail on Windows, it takes the inherited PATH down with it. Storage is `fs.statfs` plus an in-process walk; python is whichever of `python`/`py`/`python3` answers first (`PYTHONS`, `runPython`, `pythonBin`); paths join with `path.delimiter`. A new feature here gets checked on both or it is half a feature.
- **The default is "nothing configured", never somebody's machine.** `loadInstances()` used to seed a hardcoded llama.cpp instance — a named 30B gguf under `/media/al/…` — whenever the list was empty, so every fresh install inherited a phantom instance pointing at a path it does not have, and a plain GET of the list wrote prefs to put it there. The panel draws the empty case. Reads do not write.
- **`llamacpp.advertiseHost` is the endpoint's host, defaulting to loopback.** It was the constant `172.18.0.1` — one machine's Docker bridge — which is what the panel showed and what `registerEndpoint()` wrote into `openclaw.json`, so on every other install the provider pointed at an address nothing answers on. The server binds `0.0.0.0` either way; the setting is for a stack whose clients live in containers.
- **A model name from a request body is a leaf, and it is checked twice.** `/api/models` is open to every role that holds `read` — and that name is used two ways that both punish a separator: joined onto a directory something then deletes, and interpolated into the shell string of an `installCmd`. So `safeModelName()` gates the shape and install additionally requires the name to be one from the catalogue. Deleting resolves through `modelFile()`, which can only return a file: three of the four tools used to resolve *any* model to the models **directory**, which then went to `rmSync(..., {recursive: true})` — one click on one model emptied the folder.
- HuggingFace ids are validated before becoming a path (the old `/`-only replace left `..\` alone, which is a separator on Windows), and delete tries `models--` *and* `datasets--`, because the list has always shown datasets and delete only knew about models. `str(r.last_accessed)` from current `huggingface_hub` is a float of epoch seconds, so `_isoDate()` normalises it — handed to `new Date()` raw it is **Invalid Date**, which is what every row of that table showed.
- `test/models.test.js` covers all of it without Ollama, python, `llama-server` or a GPU.

### `/api/v1` client layer
- Spec: `PROTOCOL.md`. Developer guides: `docs/api/` (getting started, device app guide, agent guide, cookbook). Code: `modules/api-v1/`. Mint tokens with `npm run token -- issue --name x --preset admin|agent|phone|watch|viewer`. Adding a scope family does **not** reach devices already paired — their token holds the list it was minted with; `npm run token -- grant <deviceId> --preset phone` re-applies a preset without re-pairing.
- OpenAPI: `modules/api-v1/openapi.js` is the source; `docs/api/openapi.json` is generated from it (`npm run openapi > docs/api/openapi.json`) and `test/openapi.test.js` fails if it is stale or if any Express route is missing from it. When adding or changing a route, update `openapi.js` and regenerate.
- **DOCA is an MCP server too** (since 2.168.0, `modules/api-v1/mcp-server.js`, `POST /api/v1/mcp`, TODO H9.2): any MCP client (Claude Code, Cursor, Claude Desktop) connects over streamable HTTP with a paired device's bearer token and talks to the hive *as that device* — `doca_chat` posts through `harness.post()` and waits on the bus for that turn's outcome, `doca_conversations` lists what the device's person may open, `doca_recipes` lists and runs recipes as that person. `tools/list` offers only what the token's scopes allow (`harness:chat`, `harness:sessions`), so a viewer token gets none. `test/mcp-server.test.js` connects DOCA's own MCP client to it, which is the interop check.
- **DOCA is an AG-UI agent too** (since 2.187.0, `modules/api-v1/agui.js`, `POST /api/v1/agui`, TODO H9.2): an AG-UI front end (CopilotKit and the like) posts RunAgentInput with a device token holding `harness:chat` and reads AG-UI's events over SSE — the turn is `harness.post()` as that device and the events are the bus's for that turn, renamed (text deltas, tool call/args/end/result paired in order, `RUN_FINISHED` or `RUN_ERROR`, a question for the device as `CUSTOM doca.prompt`). The stream subscribes like any client's (`bus.subscribe`), because ephemeral deltas reach only a listening device. A thread is a conversation (`agui-threads` maps a foreign `threadId` per device). The front end's own tools and `state` are not used and a `doca.note` says so. `test/agui.test.js`.
- **And an A2A agent** (since 2.189.0, `modules/api-v1/a2a.js`): the agent card is public at `/.well-known/agent-card.json` (and `agent.json`) — the gate reads the rights table for `/.well-known/` paths, which otherwise count as panel pages — and `POST /api/v1/a2a` is JSON-RPC: `message/send` runs the text parts as the device's turn and answers with the Task (completed with the answer as message and artifact, failed, canceled; `configuration.blocking: false` answers `working` at once), `tasks/get`, `tasks/cancel`. A `contextId` is a conversation (`a2a-contexts` maps a foreign one per device). Text only, no streaming, tasks kept in memory an hour. `test/a2a.test.js`.
- **A device's command job is a run** (since 2.195.0, `api-v1/jobs.js`, TODO H11.2): `runAsJob` records it in `runs` (kind `job`, its `job_` id, `detail`: command, device, params, then the output tail and result), so `GET /api/v1/jobs/:id` answers after a restart or past the in-memory cap, and `runs.recoverJobs()` at start marks one a restart cut off as failed — interrupted.
- `/api/v1/harness/*` (`modules/api-v1/harness.js`) is how a **device talks to the agent**; `/api/v1/agent/*` is how the **agent acts on devices**. Opposite directions, opposite scopes (`harness:*` vs `agent`), and neither implies the other — do not merge them under one prefix however much the words suggest it. The adapter calls `harness/agent.turn()` and owns no conversation state, so the charter, the prompt order and proposals-need-a-click are the same ones the dashboard console gets; a device can read a proposal and never apply one.
- A turn's answer does **not** come back in the POST. `POST /harness/messages` returns `202 {turnId}` and the turn is published on the bus (`agent.turn` durable, `agent.text`/`agent.tool` ephemeral), so every client the user owns sees the same conversation and one that reconnects replays it. `agent.text` deltas go **only to the device that posted**: the bus has no per-type subscription, so a watch cannot decline them, and a token it cannot read is radio time it pays for. One turn per conversation (`409 turn_in_flight`) — two devices posting into one transcript would interleave it. The adapter also tags the turn with the posting device (`clientOf()`), and the transcript it returns carries `from` per row.
- Durable state goes to `DOCA_DATA_DIR` (default `.doca/`, gitignored); set it to a temp dir when experimenting.
- `server.js` exports `createApp()`; it only listens when run directly.

### The frontend (`public/`)
- One ~88 KB `index.html` and ~96 **classic** scripts in `public/js/` — no build step, no bundler, no framework, no ES modules. Every file is a `<script>` in global scope and the handlers are inline `onclick=` attributes calling those globals, which is why nothing here can `import` and why renaming a function means grepping `index.html` for it first.
- `nav.js` routes the pages (`NAV_TABS`, `nav()`); `nav-groups.js` draws them in groups (since 2.226.0; now Controls (Controls, Ambient) · Agents · Machines · Hub · Field · Settings — Field holds Models, MCP, Connectors and API keys since 2.236.0, the last two Settings panels shown as pages by `field-pages.js`, an old `settingsSubNav("keys"|"connectors")` landing there) — the header one pill per group, the open group showing its pages, the phone's bar the groups with a menu for a group of several. `test/nav-groups.test.js` holds every page in exactly one group.
- **A harness parameter with no box in the panel is a parameter nobody can set.** The ⚙ config form is rendered from `HARNESS_PARAMS` in `public/js/harness/param-table.js` (drawn by `harness/params.js`) — `{key, label, unit, attrs, hint}` per row — and `defaultParams()` in `modules/harness/providers.js` is the other half of the pair. `test/harness-awareness.test.js` greps the table against it so the two cannot drift. `contextWindow` shipped without a field in exactly this way.
- **`hint` is not decoration.** This panel is meant to end up in front of people who do not know what top-p is, and the hint is the only place anything gets explained. A new parameter without one is unfinished.
- **The `min`/`max` in `attrs` clamp a saved value, they do not advise.** The form writes back what the box holds, so a `max` set to yesterday's sensible ceiling silently rewrites a working config the next time somebody saves an unrelated field — which is how a 128 k ceiling would quietly undo a million-token window. Set them wide enough to catch a typo and no tighter.
- **How full the window is, is one ring drawn from one object.** `contextRingHtml()` in `agent-ui/context-meter.js` takes `budget.report()` — the `usage` event while a turn runs — or `status().context` / the history payload's `context` when a chat is opened, and both chats render it from the same fields, so the floating panel and the console cannot describe the same window differently. The light-orange band is the part of the window **past the fold point** (`compactAt`/`compactTokens`, whichever is lower, as a share of the window), drawn *over* the used arc and translucent: under it, it would disappear at the moment it starts to matter. It is not a warning colour — that is `budget.warning()` at `warnAt` — it is where older messages stop being kept as written. No window declared means no ring at all, the same rule every percentage here follows.
- **`tok/s` is model time, not wall-clock.** `budget` accumulates `ms` measured around the provider call only, so a turn that spent forty seconds in a `shell` tool is not reported as a slow model; `tokenRateEl()` draws it as one line under the finished answer, and it is `null` rather than `0` when nothing measured it.
- The ⚙ panel re-fetches its metadata on open (`_harnessLoadMeta(true)`) because the tool list is dynamic — starting an MCP server changes it — and `_harnessDisabledTools()` starts from the saved list rather than reading absent checkboxes as unticked.

### Media, downloads and Back on a phone
- **A picture, a video or a sound opens in the page: `public/js/agent-ui/media-viewer.js`** (since 2.144.0). `mediaViewerOpen()` is full screen with pinch, drag, double-tap and wheel zoom, and `overlayBack(close)` pushes one history entry so the phone's Back closes it instead of leaving the panel (a chat image used to open as a page of its own: no zoom, and Back reloaded everything). - **What a turn's events mean is decided once: `public/js/agent-ui/event-sink.js`** (since 2.143.0). `agentEventSink(ui)` holds the state every chat used to keep its own copy of — the open tool fold, the waiting row rewritten in place, failover and warning notes, errors — and `agentApprovalEvent()` the three approval states (refused note; answered settles the card and closes the popup; asked draws card and popup). ### Projects: which environment a command runs in
- **Per project, visible, and inside the command line** (`modules/projects/env.js`, since 2.134.0). `chosen(p)` is a project venv (default when one exists) or the machine's Python (`p.env.python`); `vars(p)` + `wrap(p, cmd)` put the venv's bin and `node_modules/.bin` first. The `wrap` is load-bearing: scripted commands run in `bash -lc`, whose profile prepends `~/.local/bin` and pyenv shims *after* the environment we pass, so an env var alone leaves the venv behind the machine's python.

### Projects: chat tabs, modes and per-conversation approval (since 2.149.0, asked 2026-10-04)
- **A project has as many conversations as tabs** (`projects/chat.js`, `projects/chat-tabs.js`; `GET/POST /api/projects/:id/chats`). Every conversation bound to the project (`session.projectId`) is a tab, and what one starts — a specialist's mission, a work chat below it — opens beside it once, marked ↳ (`chats()` lists them via `forSession`, so nothing new is stored for it). Each tab has its own message area, so a turn running in a background tab keeps drawing in its own place. Which tabs are open is per browser (localStorage): it is how a screen is arranged, not a fact about the project. Closing a tab leaves the conversation; ▾ lists them all, to reopen or archive.
- **A conversation has a mode** (`harness/modes.js`: Agent, Plan, Ask, Debug; `session.mode`). Plan and Ask refuse, by code, every call `turn/handoff.isWork` counts as work — the same line the Orchestrator's hand-off draws, so the two cannot disagree — and the mode's block reaches the prompt once per turn (`turnPreamble`). Approving a plan in Plan mode switches the conversation to Agent and starts the work. Debug is a method in the prompt.
- **A conversation can have its own approval switch** (`session.approval`: auto | manual | null = the panel's; `modes.approvalMode`, read by `approval.gate`). It is what lets an agent act unasked, so only a host sets it (`tab-routes.js`); Unattended stays the panel's alone.
- **The Harness console has tabs too** (`harness-console/tabs.js`): the Orchestrator first and pinned, a conversation opened from the side list becomes a tab, what an open tab starts opens beside it once (↳); drawn with the Projects tabs' styles.
- **What is lined up for a conversation folds above its composer** (`agent-ui/side-fold.js`, `GET /api/harness/sessions/:id/inbox`): the waiting messages, each withdrawable before it is read, and the plan with each step's state. The console and the Projects chat both draw it; `agent-ui/conv-bar.js` draws the mode, approval and model switches for both.

### Projects: parallel work in git worktrees (since 2.171.0, `modules/projects/worktrees.js`; TODO H7.3)
- **A conversation can work in its own git worktree** — a second folder of the same repository, on its own branch, beside it at `<repo>.worktrees/<branch>` (inside the same allowed root, outside the tree, so the main folder's `git status` stays clean). The worktree is `session.worktree`; `projects/store.forSession()` hands that conversation — and its missions and work chats, up the same parent chain — the project with `root` set to the worktree and `mainRoot` kept, so every tool (through `common.cwd`), named commands (`run.js`), checkpoints (their own shadow repository) and the brief (which says so, cached per root) work there without each knowing about worktrees. The `project` tool's `worktree` / `worktree_status` / `worktree_remove`, and ＋⑂ on the Projects chat tabs (`POST /api/projects/:id/chats {worktree: true}`), make and end one; removing refuses uncommitted work unless forced, and the branch stays. Merging it back is the person's call, or a git step the agent asks for.

### Projects: pages, a document with a chat beside it (since 2.186.0, `modules/projects/pages.js`; TODO H9.4)
- **A project is the space and its `.md` files are the pages** — plain files that Obsidian, VS Code or git read as they are, rendered and edited by the Projects editor (md-doc.js); no second document store. `POST /api/projects/:id/pages {title}` makes `<slug>.md` beginning with `# Title`, never over an existing file (＋📄 on the chat tabs).

- **A tab holds a Monaco model or a view, never assume a model** (`public/js/projects/preview.js`, since 2.130.0). ### Inference services (`modules/services.js`)
- **The panel owns the host directories its containers mount, and creates them before `docker run`.** An image's init may expect a bind target to exist and be writable by `WANTED_UID`; a bind source missing on the host is created by Docker as root, which is the one owner that step cannot write as. When it fails there the container exits 1 and Docker restart-loops it — `Up` for seconds, `Restarts` climbing, and the port answering `000` forever. `handleStart()` therefore mkdirs *and chowns to the caller's uid/gid* every host directory it mounts, not only the top-level one. Cost: the ComfyUI service, 2026-09-30 — `docs/audits/2026-09-30-comfyui-basedir-mount.md`, fixed in 2.116.2.
- **Start waits for the service to answer** (since 2.204.0, `services.js waitReady`): after `docker run` it polls the service's own route (`READY`) and watches the container; one that restarts or exits is reported with its last log lines and a reason (`diagnose()`: a PyTorch too old for the GPU, out of memory, no GPU in Docker, a taken port) and removed, so it does not loop behind a "started". The Services row shows a restarting or exited container as such, with Stop. Found live: Kokoro's GPU image (PyTorch 2.8 + CUDA 12.6) has no kernels for an RTX 50-series GPU.
- **A start is not a service, and a service is not a tool.** `docker ps` says `Up` as soon as the entrypoint is alive, which for these images is minutes before the application answers; check the port and the image's own version route (`/system_stats`, `/sdapi/v1/…`) before calling it started. And an API that answers does not mean it can do the work: ComfyUI without a checkpoint in `ComfyUI/models/checkpoints` serves, queues and generates nothing.
- **A running release is a copy under `.releases/<version>/`.** Editing one there fixes the panel in front of you and nothing else — the same change in the tree is what a later release actually carries. Say so when it happens, and keep the backup the write already makes under `.doca/harness/backups/`.

### Environment gotchas (not bugs)
- The dashboard manages an *external* Docker Compose stack and various AI CLIs. Those tools (Docker, Ollama, nvidia-smi, huggingface-cli, etc.) are **not installed by default**. Panels that shell out to them (e.g. "All Containers" showing `docker: not found`, GPU stats, model managers) will show errors/empty state. This is expected and does not indicate the app is broken — installing Docker/etc. is optional and only needed to exercise those specific panels.
- Some sidebar stats (CPU temp, GPU) read host sensors that are unavailable in the VM and render as `-`.
- **The container CLI is `modules/containers.js`'s `cli()`** (since 2.169.0, TODO H1.6): `docker` (Engine, Docker Desktop, Colima, OrbStack) else `podman`, or `DOCA_CONTAINER_CLI`; every call site — services, the Docker tab, logs, the stack card's compose (Settings → OpenClaw → Stack since 2.199.0: it is OpenClaw's compose, so it sits in OpenClaw's group, drawn only where OpenClaw is installed), computers — goes through it. Podman takes the same arguments for what DOCA runs, but no Podman host has run it yet: the resolver is tested, a real Podman is not.
- **GPUs are read by `modules/gpu.js`, whoever made them** (since 2.167.0, TODO H1.4): nvidia-smi on any OS, rocm-smi's JSON for AMD, ioreg's IOAccelerator statistics for Apple silicon (utilisation and the shared memory in use, no sudo), the sysfs clock for Intel on Linux, and the adapters by name and memory on Windows without nvidia-smi. A reading a tool does not give is `null` and the sidebar draws a dash; Apple's memory is labelled shared (`unified: true`). The AMD and Apple parsers are tested against samples written in the tools' documented shape — no such GPU is on the machines this is built on, so a real one may still disagree.
- Default paths (`COMPOSE_DIR`, `CONFIG_PATH`, `SKILLS_DIR`, `WORKSPACE_DIR`, `SNAPSHOT_DIR`) derive from `~` and may not exist; override via env vars (see README "Environment Variables") or in **Settings → System → Paths**, which also creates them. Precedence is saved-in-prefs > env > default, resolved in `modules/paths.js`: overrides are written into `process.env` at boot before the constants are computed, so a saved change needs a restart, and anything acting on a path outside boot should call `paths.describe()` rather than trusting the captured constant.
- Writes go through `writeFileSafe()` / `saveConfig()` / `savePrefs()` in `modules/utils.js`, which create missing directories and keep a `.bak`. Do not reintroduce a bare `fs.writeFileSync` for a user-facing file: a config path whose parent does not exist is a normal first-run state, not an error to show the user.
- No hypervisor and no MCP server is installed either. The **VMs** tab saying `virsh not found` and the **MCP** tab being empty are correct first-run states.
- Runtime prefs are written to `.dashboard-prefs.json` and certs to `.certs/` (both gitignored).
- **The machine this is actually tested on is a Windows box.** The repo lives at `D:\doca\doca\DOCA` on the host named `portal`, beside its three clients; the panel itself runs there. An agent driving that machine over a desktop bridge should not assume it has a shell on it — mounting `D:\` into an agent workspace has been broken since a Windows update on 2026-09-08 — so the loop that works is: write files through the bridge's file-commit tool, leave a `.cmd` wrapper in `D:\doca\` that redirects **all** of its output to a log file, have it double-clicked, then read the log back. `run-both.cmd`, `test-docadesk.cmd`, `build3.cmd` and the `release-X.Y.Z.cmd` files are that pattern; copy the newest rather than inventing a new shape. A wrapper that prints to a console nobody can read has verified nothing.
